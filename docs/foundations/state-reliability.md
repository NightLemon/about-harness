# 状态与可靠执行

可靠执行的目标不是“永不失败”，而是让每次失败都可分类、可停止、可安全重试、可恢复，并且不会因为恢复而重复产生副作用。只保存对话历史不等于保存了运行状态；可靠 harness 还要知道动作执行到哪里、外部系统是否已经接受动作，以及下一步能否继续。

## 先分清三类状态

| 状态层 | 典型内容 | 主要写入者 | 丢失后的风险 |
| --- | --- | --- | --- |
| 控制状态 | run 状态、step、预算、停止原因、批准结果 | controller | 无限循环、越过预算、错误宣告完成 |
| Adapter 状态 | response/call ID、消息游标、模型连续状态 | adapter | 重放错误上下文、丢失工具调用连续性 |
| 业务状态 | 文件版本、订单号、消息 ID、外部回执 | tool 与目标系统 | 重复写入、重复付款、无法判断是否成功 |

Checkpoint（检查点）是恢复控制状态和 adapter 状态的持久快照；它不能替代外部系统的业务记录。恢复时必须同时核对检查点、工具执行台账和目标系统回执，不能因为检查点里没有结果就推断动作从未发生。

## 状态机与不变量

一个 run 至少经历以下状态：

```text
created ──契约通过──> running ──需要批准──> waiting-approval
                         │                         │
                         │<────批准且预算仍有效────┘
                         ├──完成条件成立──────────> completed
                         ├──不可恢复错误──────────> failed
                         └──取消/预算/超时────────> cancelled 或 stopped
```

状态转换只能由 controller 写入。模型可以提出“完成”，工具可以返回“成功”，但它们都不能直接把 run 改为 `completed`。每次转换至少检查四个不变量：

1. 终态不可重新进入 `running`；若要继续，应创建带来源引用的新 run。
2. `completed` 必须绑定验收证据，不能只绑定模型文本。
3. step、model call、tool call 和 cost 计数只能单调增加，恢复后不能归零。
4. `waiting-approval` 仍受总 Deadline（截止时间）和取消信号约束，批准不是无限期暂停预算。

## Deadline 与真正的超时

Timeout（超时）描述单次操作最多等待多久；deadline 描述整个 run 最晚何时结束。controller 应使用单调时钟计算 `deadline = start + budget`，并把“剩余时间”逐层传给 model、tool、队列和子任务。墙上时钟适合日志时间戳，不适合计算耗时，因为系统时间可能跳变。

仅在调用返回后检查 deadline 属于软边界：它能拒绝迟到结果，却不能中止一个永久阻塞的调用。硬边界需要下游客户端的请求 timeout、可取消任务，或可终止的进程/容器。记录证据时要明确区分“结果因迟到被丢弃”和“调用已被抢占”，两者的资源占用与副作用风险不同。

## 什么可以重试

Retry（重试）不是“失败后再来一次”，而是对已分类、可恢复且仍在预算内的失败执行新尝试。

| 失败类型 | 默认处理 | 原因 |
| --- | --- | --- |
| 限流、短暂网络错误、可恢复资源冲突 | 有限指数退避，并保留同一幂等键 | 下一次可能成功 |
| schema/参数错误 | 返回精确校验错误，允许产生修正后的新动作 | 原样重试仍会失败 |
| 认证或权限拒绝 | 停止并请求正确权限 | 重试不能改变授权 |
| 确定性测试或验收失败 | 改变假设或实现后重新验证 | 失败来自方案，不是传输 |
| 副作用结果不明 | 先按幂等键查询台账或目标系统 | 盲目重试可能重复执行 |

退避 trace 中的 `delay_ms` 必须与实际 sleeper 收到的值一致。达到尝试次数、deadline 或费用上限时立即停止；不能让重试拥有独立于 run 的无限预算。

## 幂等与副作用

Idempotency（幂等）表示同一逻辑操作重复提交时，外部结果与执行一次相同。所谓“恰好一次”通常不是单个进程能保证的；更可行的是至少一次投递，加上稳定幂等键、结果缓存和对账。

幂等键应绑定操作作用域和规范化参数，例如 `tenant + tool + business_object + operation_version`，并同时保存参数 hash。若同一个键对应不同参数，必须作为冲突拒绝，而不是复用旧结果。

副作用的安全顺序是：

1. 写入 action intent：tool、规范化参数 hash、幂等键和预算快照；
2. 执行工具，并让目标系统保存同一幂等键；
3. 保存结构化结果与外部回执；
4. 提交包含 adapter position 和计数器的新检查点。

进程可能在任意两步之间崩溃。尤其是“外部动作成功，但本地结果尚未保存”这一窗口，恢复时必须先查询目标系统或幂等台账。直接再次执行是最危险的默认值。

## 取消与并发

取消是状态转换，不是只设置一个 UI 标志。父任务取消要传播到子任务、模型流、工具进程、退避 sleeper、队列和等待中的批准；每个边界都要决定能否抢占、何时检查信号、如何处理迟到结果。

多个 worker 可能同时恢复同一 run，因此检查点要有版本或 compare-and-swap（比较并交换）条件。并发写同一文件或业务对象还需要所有权、锁、隔离 worktree，或目标系统提供的条件更新。只在内存里加锁不能保护跨进程恢复。

## 恢复决策表

恢复程序先回答“最后一个可证明的事实是什么”，再选择动作：

| 已有证据 | 恢复动作 |
| --- | --- |
| 只有 intent，没有外部回执 | 查询目标系统；确认未执行后才重试 |
| 有成功回执，没有检查点 | 复用结果并补写检查点，不重复工具调用 |
| 有检查点，但 adapter state 无法恢复 | 失败关闭，创建新 run 并引用旧 trace |
| 参数 hash 与幂等键台账冲突 | 标记 contract failure，禁止覆盖旧结果 |
| run 已取消，但收到迟到成功结果 | 记录迟到结果；是否接受副作用按业务补偿策略处理，不重开 run |

补偿动作不是自动回滚。发出一条反向操作也可能失败，并且不能抹去已经发送的邮件、已读消息或外部观察。对不可逆动作，应在执行前批准和预览，而不是把希望寄托在补偿上。

## 动手验证

前置条件是 Python 3.11+、仓库已执行 `uv sync --frozen --offline`，输入使用内置 fake adapter，不读取凭据也不访问网络。

```bash
uv run pytest -q lab/tests/test_loop.py -k "retry or checkpoint or cancellation or timeout"
```

预期所选测试全部通过。重点断言不是最终状态本身，而是：重试次数有限且实际等待值匹配 trace；恢复保留 adapter position 与累计计数；取消和 deadline 返回明确 `stop_reason`；迟到 action 不能把 run 改成完成。

若测试失败，先保留失败输出并按 retry、checkpoint、cancel 或 timeout 分类，不要增加重试次数掩盖问题。本命令只读取 fixture，无额外清理；若为了学习修改了测试或实现，用精确 `git diff` 审阅并只还原自己改动的文件。完整回归命令是 `uv run pytest`。

## 当前实现边界

本项目最小 runner 提供 E1 的 fake/replay 证据：它在 adapter/tool 调用边界检查总 deadline，使用进程内幂等缓存，并能恢复 fake adapter position。它没有持久数据库、分布式锁、外部对账或强制终止任意阻塞 Python callable，因此不能证明生产环境具备恰好一次执行或硬超时。
