# 什么是 Agent Harness

## 一句话定义

**Agent harness 是让模型能够在约束下持续观察、决策、行动和验证的运行与控制系统。** 它连接用户目标、模型、上下文、工具和外部环境，并管理权限、状态与反馈。

“Harness”原意是挽具：它既让能力可以被利用，也限定力量如何作用。不同社区没有唯一严格定义；本文采用工程上的广义定义，并在涉及具体产品时写明产品名。

## 本项目的范围

本项目以**软件工作 agent**为主：coding、文档、研究、浏览器操作与工程自动化。原理也可迁移到其他数字 agent，但不试图覆盖模型训练框架、GPU 推理服务器、机器人控制系统，或名为 Harness 的 CI/CD 商业产品。具体到 Codex、Pi、Claude Code 时，“harness”既可指产品整体，也可指其中承载 agent 循环的层；正文会明确产品名和可操作的配置表面（surface）。

写作约定：普通概念在英文句中写作小写 `harness`/`agent`；页面标题、句首和产品名称可大写。`surface` 指同一产品的 CLI、IDE、桌面、Web 或云端等使用/执行表面，不等同于模型供应商（provider）。

## 模型、Agent 与 Harness

| 概念 | 主要职责 | 不负责什么 |
| --- | --- | --- |
| 模型 | 根据当前输入预测或生成下一步内容/动作 | 不天然拥有文件、网络、长期记忆或真实执行权 |
| Agent | 围绕目标进行多步决策，选择动作并根据结果继续 | 不必自行提供 sandbox、会话存储或 UI |
| Harness | 组装 agent 循环，提供上下文、工具、策略、状态、反馈和界面 | 不能凭空补足模型的基础推理能力 |

在口语里，人们常把 agent 产品整体叫作 agent，也会把 coding agent 叫 harness。沟通时最有效的做法不是争论名称，而是问：“这个组件负责决策，还是负责承载与约束决策？”

## Harness 的最小组成

一个可用的 coding harness 至少需要：

1. **输入与消息编排**：合并系统规则、项目规则、用户任务与工具结果。
2. **模型适配器**：调用模型，处理流式输出、工具调用与错误。
3. **工具执行器**：读写文件、运行命令或访问服务。
4. **循环控制器**：决定何时继续、重试、压缩、暂停或结束。
5. **权限边界**：限制文件、网络、命令和外部副作用。
6. **会话状态**：保存消息、文件状态、计划或检查点。
7. **反馈与可观测性**：把退出码、测试结果、成本和轨迹暴露出来。

缺少反馈的系统更像“自动生成器”；缺少控制边界的系统只是把风险扩大。

## 为什么同一个模型表现不同

同一个模型在两个 harness 中表现不同，常见原因有：

- 系统提示和持久指令的内容、顺序与长度不同；
- 工具名称、描述、参数 schema 和返回格式不同；
- 一个 harness 自动搜索，另一个等待模型显式搜索；
- 上下文压缩的触发点与摘要保留策略不同；
- sandbox、审批或网络限制让某条路径不可用；
- 错误是否原样反馈、是否自动重试、最大回合数不同；
- 模型供应商、模型快照、推理强度或采样设置并不相同。

因此，比较模型时必须同时记录 harness 与配置；比较 harness 时也必须固定模型、任务和预算。

## Harness 不是什么

- 不是单个 system prompt；提示只是上下文层的一部分。
- 不是工具数量竞赛；更多工具可能增加选择错误和攻击面。
- 不是“全自动”的同义词；高质量 harness 也可以把关键步骤交给人审批。
- 不是模型微调；它在推理时组织环境，不改变模型权重。
- 不等于模型训练框架或只负责托管推理的 API server；本文关注推理时的 agent 工作循环。
