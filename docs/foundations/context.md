# 上下文工程

上下文是模型在当前一步实际看到的信息。它通常包括系统指令、项目规则、会话消息、文件片段、工具返回、计划、记忆和压缩摘要。

## 四个质量维度

好的上下文不是“越多越好”，而是：

- **相关**：直接影响当前决策；
- **可靠**：来源明确、足够新、没有被未可信内容冒充指令；
- **可定位**：包含文件、行号、URL 或数据键；
- **经济**：用尽量少的 token 保留决策所需信息。

## 上下文预算

名义上下文窗口不是可全部自由使用的空间。系统指令、工具 schema、历史、输出预算都要占用。接近窗口上限时，注意力可能稀释，harness 也可能压缩旧消息。

把预算分成四类：

| 类别 | 应保留 | 应压缩或移出 |
| --- | --- | --- |
| 长期规则 | 构建命令、禁区、非显然约定 | 教程式解释、通用常识 |
| 当前任务 | 目标、约束、验收、关键文件 | 已否定方案的冗长过程 |
| 证据 | 错误、测试摘要、关键 diff | 重复日志、完整依赖安装输出 |
| 运行状态 | 已改文件、剩余项、决策 | 不再相关的闲聊与探索 |

## 检索优于预加载

大型仓库不要在启动时把架构文档、API 文档和文件树全部塞入模型。给模型一张“路由图”：入口文件、搜索工具、文档索引、应优先读取的目录。让它按需检索，并把大结果先过滤或汇总。

但检索并非总是更好。每次都必须遵守、且模型无法从代码推断的少量规则，应直接放进持久指令。判断问题是：“不预加载这条信息，模型会不会经常做出不可逆或昂贵的错误？”

## 压缩是有损操作

自动压缩通常把旧对话总结为较短状态。容易丢失：被否定方案、精确数值、文件清单、未解决边界条件和用户原话中的细微约束。

长任务在压缩前应维护可恢复状态：

```md
# TASK_STATE.md
- 目标：...
- 不得改变：...
- 已确认事实：...
- 已修改文件：...
- 验证命令与结果：...
- 剩余工作：...
- 被否定方案及原因：...
```

这个文件不是所有任务都需要。它适合跨会话、即将压缩、多人/多 agent 或高风险迁移；短任务使用计划与最终摘要即可。

## 工具输出也是上下文

常见污染来自测试打印几万行、读取压缩文件、递归列出依赖目录。Harness 或工具应支持：过滤、分页、最大输出、结构化字段以及指向完整 artifact 的引用。不要简单截断最后部分，因为错误摘要可能位于开头。

## 记忆与指令不同

- **指令**表达应如何工作，优先级高、应受版本控制。
- **记忆**保存过去可能有用的事实或偏好，需要允许过期与纠正。
- **任务状态**描述这一次工作进行到哪里，完成后通常归档。

把易变事实写成永久指令，会制造陈旧真相；把强约束只留在自动记忆里，则难以审计。

## 上下文卫生检查

遇到表现下降时，先问：当前目标还在吗？关键约束是否在压缩后保留？工具输出是否挤占大部分窗口？持久指令是否互相冲突？会话是否混入另一个任务？如果同一问题纠正两次仍不收敛，保存已验证状态并新开干净会话，通常比继续堆叠纠错更有效。
