# 多 Agent 编排

Multi-agent（多 Agent）编排的价值来自上下文隔离、专长、独立复核和真正可并行的工作，不来自角色数量。一个边界清晰、工具充分的单 Agent loop，通常比多个角色反复转述同一上下文更便宜、更快，也更容易归因。

## 先判断是否值得拆分

只有满足至少一个可测条件时才增加 Agent：

- 子问题输入和输出可以写成独立契约；
- 调查能够并行，而且不会竞争同一可变资源；
- 单个上下文会被互不相关的材料淹没；
- 任务需要与实现上下文隔离的独立验证；
- 不同子任务确实需要不同工具、权限或领域知识。

以下情况通常不值得拆分：步骤存在严格先后依赖、所有 worker 都必须读取相同长上下文、最终修改集中在一个小文件，或没有可靠方法合并冲突结论。若无法说明新增 Agent 解决哪个瓶颈及怎样验收，先保留单 Agent 基线。

## 常见拓扑及适用边界

| 拓扑 | 适用问题 | 主要风险 |
| --- | --- | --- |
| Router（路由器）→ specialist（专门执行者） | 请求类型明确、责任互斥 | 路由错误、专长标签过时 |
| Planner（规划者）→ workers → verifier（验证者） | 可分解的多文件或多来源任务 | 计划脱离现场、合并成本高 |
| Supervisor loop（监督循环） | 子问题在执行中动态出现 | 循环委派、全局预算失控 |
| Map-reduce（分片汇总） | 大量独立文档、记录或案例 | 分片遗漏、摘要丢失例外 |
| Debate/jury（辩论或评审团） | 主观方案比较、风险枚举 | 多数票制造虚假确定性 |

Debate 可以暴露假设，却不能代替测试、来源和业务负责人。多个 Agent 给出相同结论也不自动构成独立证据；它们可能共享模型、提示、检索结果和同一错误前提。

## 委派契约

父 Agent 应把每个子任务变成可验证的工作单，而不是一句“帮我看看”：

```text
task_id / parent_id      唯一身份与来源
goal / non_goals         目标、完成条件和明确禁区
input_refs               固定文件、版本、artifact 或问题范围
allowed_tools            可调用工具与是否允许再委派
read_scope / write_scope 可读写资源和唯一所有者
budget / deadline        step、token、费用、时间和重试上限
output_schema            结论、证据、修改、风险和未决项
stop_conditions          完成、失败、冲突、需授权或取消
report_channel           结果交给谁、何时回报进度
```

子 Agent 不自动继承父级全部上下文、凭据或工具。父级也不能把自己没有的权限“转授”给子级。若允许再委派，契约必须限制最大深度、总并发和剩余预算，否则 Supervisor 可能通过不断创建子任务逃逸终止条件。

## 权限树与预算树

权限只能沿委派树收窄：子任务的工具、路径、数据域和外部副作用权限，必须是父任务权限的子集。处理公开资料的 researcher 不需要写仓库；只运行测试的 verifier 不需要发布权限；implementer 也不应顺便读取私人数据。

预算则需要“预留—消费—归还”模型。父级给 worker 预留 20 秒，并不意味着全局 deadline 增加 20 秒；并行任务共享墙钟，但 token、费用和工具调用仍要累计。子任务结束后归还未使用预算，超支请求回到父级决定，不能由子级自动扩大。

全局停止优先于局部目标。父级取消、费用耗尽或风险升级时，要向所有后代传播取消，并拒绝迟到结果触发新的副作用。

## 用 Artifact 交接，而不是共享长对话

Artifact（产物）可以是固定 commit、补丁、测试输出、结构化 JSON、来源清单或带 hash 的摘要。它应包含版本、生产者、输入引用、证据边界和缺失项。父级根据 artifact 组合结果，而不是要求每个 Agent 重放完整聊天记录。

共享可变计划会产生 lost update（更新丢失）：两个 worker 同时改写同一段状态，后写者覆盖前写者。更安全的默认值是：

1. 并行调查只读同一基线，各自写独立结果；
2. 并行实现使用独立 worktree、目录或明确不重叠的文件所有权；
3. 单一 integrator（集成者）按依赖顺序合并；
4. verifier 针对合并后的真实状态运行，而不是验证各自分支的摘要。

“文件不重叠”也不保证语义不冲突。一个 worker 修改 schema，另一个 worker 编写旧 schema 的消费者，即使 Git 没有冲突也会失败，因此委派契约还要声明接口版本和依赖边。

## 消息与结果交付语义

跨进程或队列的消息通常可能重复、延迟、乱序或丢失。每条任务和结果至少携带 task ID、attempt、sequence/revision、输入版本和幂等键。接收方先去重，再检查结果是否仍对应当前基线。

迟到结果不能覆盖较新的决策；已取消 worker 的输出可保留为调查证据，但默认不能触发写操作。父级等待多个 worker 时，要区分：

- **完成**：结果满足 schema 和证据要求；
- **需关注**：权限、歧义或失败需要父级处理；
- **观察超时**：尚未看到新事件，不等于 worker 已失败；
- **终止**：权威运行状态确认任务已结束或句柄不存在。

不能因为一次轮询超时就重启相同 worker，否则两个实例可能同时产生副作用。

## 独立验证怎样才算独立

Verifier 不应只阅读 implementer 的最终摘要。它至少读取任务契约、实际 diff/产物、执行环境和验收命令，并能访问失败输出。若验证者与执行者共享同一模型、提示和压缩摘要，报告中要说明相关性，不能把它宣传成完全独立评审。

确定性检查仍优先：构建、测试、schema、资源状态和内容 hash。主观质量可以由第二 Agent 或人工 rubric 复核，但争议必须回到具体标准和证据，不能用多数票抹平。父级负责最终判断；“所有子 Agent 都说完成”不是完成条件。

## 工作例：并行调查、单点写入

假设站点构建和 Python 测试同时失败：

1. 父 Agent 冻结同一 commit，派两个只读 worker；一个定位前端构建，一个定位 Python 测试。
2. 两者都返回复现命令、退出码、相关文件、根因假设和不确定项，不允许修改共享 checkout。
3. 父级比较证据，若根因独立，再为 implementer 分配明确文件所有权；若都涉及同一配置，只保留一个 writer。
4. Integrator 合并后运行目标测试；verifier 在合并状态运行完整验收并检查 diff。
5. 任一 worker 需要联网、费用或新权限时，只暂停该子任务；父级继续权限内工作并决定是否升级。

并行的是独立信息收集和无冲突执行，不是让多个 Agent 抢写同一状态。

## 失败模式与恢复

| 现象 | 可能根因 | 恢复动作 |
| --- | --- | --- |
| worker 重复相同搜索 | 分工输入不互斥 | 重新按目录、问题或证据类型切分 |
| 子任务互相继续委派 | 没有深度与全局终止条件 | 取消后代，收回剩余预算 |
| 结论冲突被投票抹平 | 输出缺少证据和适用边界 | 回到原始 artifact，设计判别测试 |
| 子 Agent 使用额外工具 | 权限继承过宽 | 在执行层收窄 capability，而非补提示词 |
| 合并无 Git 冲突却测试失败 | 接口或基线发生语义冲突 | 按依赖顺序重放，并重新验证消费者 |
| worker 超时后出现双重写入 | 把观察超时误判为终止 | 查询权威状态，按幂等键对账 |
| 一个输入中的注入污染全部结果 | 未隔离来源和上下文 | 停止扇出，撤销副作用能力，重建可信输入 |

## 怎样证明多 Agent 值得

比较时保留相同任务、模型/设置、工具和验收的单 Agent 基线。至少报告：任务成功与安全事件、墙钟延迟、总 token/费用、模型和工具调用、人工介入、重复工作、委派开销、冲突数、无效/迟到结果与关键路径。

并行使墙钟变短，不代表总资源变少；验证者提高发现率，也可能增加延迟。只有目标工作负载上的质量、风险或时间收益稳定超过这些成本，才把多 Agent 设为默认。不要用“调用了几个 Agent”作为能力指标。

当前仓库没有可执行的多 Agent runner 或 E1 编排实验，本页是稳定机制和项目建议，证据等级为 E0。若要升级证据，应先锁定单 Agent 基线与固定任务，再加入可观测的委派事件、预算树、取消负例和合并冲突案例。
