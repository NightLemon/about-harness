# 人在循环中的控制点

Human-in-the-loop（人在循环中）不是“每一步都问用户”，而是把不可逆、高风险、跨信任边界或缺少业务判断的决策放到明确关口。好的人工控制既防止 agent 擅自扩大后果，也避免让用户在大量无害弹窗中形成机械同意。

## 人工参与的四种责任

1. **范围确认**：目标很大、影响未知或需要多个里程碑时，确认做什么和不做什么；
2. **动作授权**：删除、发布、付费、外发数据、权限提升等产生真实副作用前确认；
3. **歧义裁决**：多个选项会实质改变结果，而且无法从任务、项目规则或现有证据推断；
4. **结果验收**：机器规则能证明结构和行为，却不能独自证明语义、视觉、业务或伦理判断。

这四种责任不能互相替代。用户接受计划，不等于授权计划中的每个外部副作用；用户授权执行，也不等于接受最终结果。

## 先按风险而不是命令名分级

同一个工具可能既能执行无害读取，也能删除生产数据。Policy（策略）应综合以下维度判断，而不是把整个 shell、浏览器或 API 简单标为“安全”或“危险”：

- **可逆性**：能否可靠恢复，恢复是否还有新的副作用；
- **影响范围**：单个临时文件、整个仓库、一个组织还是公开互联网；
- **数据敏感度**：公开内容、内部资料、个人信息或凭据；
- **费用与资源**：调用次数、最大费用、运行时间和配额；
- **可观察性**：执行前能否 preview，执行后能否确认真实状态；
- **授权主体**：请求者是否有权代表目标账号、仓库或业务对象作决定。

可用一个简单的默认矩阵：

| 动作特征 | 默认控制 | 示例 |
| --- | --- | --- |
| 只读、范围内、无敏感数据外发 | 自动执行并记录 | 搜索仓库、读取公开文档 |
| 可逆的工作区写入，已由任务直接要求 | 自动执行、展示 diff、运行验证 | 修改源码或中文文档 |
| 会改变共享或远端状态 | 任务级独立授权，执行后核对资源 ID | push、PR、发送消息、更新远端配置 |
| 高费用、大范围或难以撤销 | 动作时批准，必要时双人复核 | 生产发布、批量删除、权限提升 |
| 目标或所有权不清 | 停止并升级 | 不确定账号、环境或数据归属 |

模型置信度不是风险控制。即使模型非常确定，高风险动作仍要经过执行层 policy；即使模型不确定，低风险调查也不必频繁打断用户。

## 授权是一条有边界的能力

一次授权至少要绑定：

```text
subject     谁发起、代表谁
verb        允许做什么动作
resource    精确目标与环境
constraints 数据、费用、次数、时间和工具限制
evidence    执行前依据与执行后验证
lifetime    单次、当前 run 或明确截止时间
fallback    拒绝、过期或失败时怎样安全停止
```

只要 verb、resource、环境、数据接收方或预期副作用发生实质变化，就要重新评估授权。把“可以修复这个页面”扩展为“可以发布网站”，或把“读取公开 issue”扩展为“读取私人仓库”，都属于越界。

长期 allowlist 只适合输入和后果都稳定、可测试的动作形态。不要把某次临时批准自动写成永久规则；也不要让仓库文本、网页内容、模型输出或工具描述替用户授予能力。

## 一个可判断的批准请求

批准请求要让用户能在不重做调查的前提下回答“同意或拒绝”。建议固定为：

```text
动作：将执行的具体操作
目标：账号、仓库、环境、资源 ID 或精确路径
理由：为什么完成目标需要它，已有证据是什么
副作用：数据去向、费用、公开范围和最坏影响
验证：执行后用什么独立信号确认成功
恢复：能否回滚，不能恢复的部分是什么
边界：本次授权不包含哪些相邻动作
替代：若拒绝，能够继续哪些安全工作
```

不要只问“是否继续”，也不要在一个请求中打包风险不同的十个动作。能安全批处理的同类动作可给出清单和总上限；不可逆动作应逐个展示最终目标和预览。

## 拒绝、过期与取消也是正常状态

用户拒绝不是工具错误，更不是让模型换一种隐蔽方式达到同一副作用。Controller 应把结果记录为 `denied`，随后选择三种路径之一：

1. 在原权限内提供明确的只读分析、补丁或 dry-run；
2. 若替代方案会改变需求，说明差异并等待新选择；
3. 没有安全替代时停止，报告已完成证据、未完成项和需要的主体。

授权等待期间仍可取消，也应有有效期。批准到达时必须重新检查 run 是否已停止、目标版本是否变化、预算是否仍足够；迟到批准不能复活终态任务。

## 减少审批疲劳

Approval fatigue（审批疲劳）会让用户不再阅读目标和副作用。优化方向不是简单减少次数，而是提高每次询问的必要性和可判断性：

- 调查阶段默认提供安全的只读工具，不为每个文件弹窗；
- 将同风险、同目标、同恢复方式的动作批量说明，并设置数量或费用上限；
- 优先展示 diff、dry-run、接收方和最终资源 ID；
- 记住同一 run 内明确拒绝的动作，避免换一种措辞重复请求；
- 对高频批准做事后分类：应自动允许、应保持询问，还是本不应提供该工具。

减少弹窗不能以扩大默认权限为代价。如果用户经常批准某类危险动作，应改进工作流、隔离环境或委托范围，而不是关闭控制点。

## 两个工作例

### 新增依赖

Agent 发现任务可通过新增 package 完成。请求应写明精确包与版本、为什么现有依赖不足、安装脚本和许可、将修改的锁文件、验证命令与恢复方式。批准“安装这个版本”不授权升级其他依赖、外发源码或发布。被拒后可保留无新依赖实现，或只提交方案比较。

### 发布文档

本地构建通过只证明生成物满足当前检查，不等于已经授权公开发布。发布请求还要列出目标站点、源 commit、将触发的 workflow、公开数据扫描、验证 URL 和回滚版本。若页面内容或源 commit 在批准后变化，应重新展示差异，而不是沿用旧批准。

## 怎样评测人工控制

至少报告：每个 run 的人工介入次数与等待时间、批准/拒绝/过期分布、可避免询问、漏掉的危险动作、授权后失败、作用域漂移和拒绝后的安全替代成功率。单独追求“批准率高”会奖励过宽请求；单独追求“询问少”会奖励静默越权。

故障注入应覆盖：批准服务不可用、批准迟到、目标版本变化、同一动作重复投递、拒绝后模型改写参数再尝试，以及批准记录缺少主体或资源。通过正常批准路径不能证明控制面可靠。

## 本项目的建议边界

本项目把仓库内只读调查和用户明确要求的可逆本地修改视为正常执行；真实 API、费用、Git 远端写入、push、PR、Pages 与 release 使用独立授权。凭据、个人数据、不可恢复删除和权限提升始终按高风险处理。项目指令负责说明协作习惯，真正的硬边界仍由 sandbox、tool policy、分支保护和目标系统权限执行。

## 自检与下一步

任取一次批准记录，第三方能否回答谁在何时允许了哪个主体对哪个资源做什么、限制是什么、结果如何验证？拒绝后是否进入可解释的安全状态？结合[安全与权限](/foundations/security)、[状态与可靠执行](/foundations/state-reliability)和[事件响应](/security/incident-response)继续演练。
