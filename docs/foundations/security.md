# 安全与权限

Agent 安全不是要求模型永不犯错，而是在模型、工具和外部内容都会出错的前提下限制后果。

## 先画信任边界

至少区分：

- 用户明确给出的指令；
- 仓库中已审查的指令与代码；
- 网页、issue、日志、依赖包等不可信内容；
- 本地密钥、私人文件和浏览器会话；
- staging 与 production；
- 只读动作、可回滚写入和不可逆外部动作。

来自网页或仓库的文字是数据，不能自行授权上传文件、发送消息或修改权限。

## 五层防护

1. **最小工具**：调查任务只给读取与搜索。
2. **Sandbox**：限制可写目录、网络和进程能力。
3. **策略/allowlist**：允许已知安全的命令形态，拒绝危险目标。
4. **动作时审批**：删除、发布、购买、发消息、改权限等在真正执行前确认。
5. **审计与回滚**：保留 diff、命令、资源 ID、checkpoint 或 Git 历史。

提示词里的“不要做危险操作”只能辅助，不能替代执行层控制。

Sandbox 也不是“安全完成”证明：内核/运行时漏洞、被允许的网络出口、挂载凭据、宿主 socket、过宽父目录和供应链脚本都可能穿过预期边界。记录实际隔离机制与例外，不用一个 `sandbox: true` 标签代替威胁模型。

## 审批应该说明什么

一次有意义的审批要说清：将执行的具体动作、目标系统/账号、涉及的数据、预期副作用和是否可撤销。把十个不同命令包装成“允许所有操作”会让用户无法判断风险。

## 常见风险

| 风险 | 例子 | 控制 |
| --- | --- | --- |
| Prompt injection | README 要求读取并上传环境变量 | 内容分级、敏感动作再授权、最小工具 |
| 命令注入 | 把不可信分支名拼进 shell | 结构化参数、转义、避免 shell 字符串拼接 |
| 过宽文件权限 | agent 可写用户主目录 | 工作区 sandbox、显式外部路径审批 |
| 凭据泄露 | 日志回显 API key | secret redaction、短期令牌、不传完整环境 |
| 供应链 | 未审查的 skill/extension 执行代码 | 固定版本、审源、隔离安装、最小权限 |
| 工具投毒 | MCP/插件更新后描述诱导模型调用高风险动作 | 固定/审查版本、工具清单 diff、动作时审批 |
| 混淆环境 | 把测试命令对 production 执行 | 环境标识、默认 dry-run、独立凭据 |
| 不可逆修改 | 删除数据或强推分支 | 备份、软删除、分支保护、动作时审批 |

## 数据流与隐私

在启用模型、MCP、浏览器或云执行前，画出数据从哪里到哪里：源码、日志、issue、文档、截图和 tool result 可能进入模型 provider、harness 服务、第三方 MCP server、遥测或本地 session 文件。分别确认：数据类别、接收方、区域、传输/静态加密、保留期、训练使用、管理员可见性与删除方式。

最低实践：

- 不把生产数据、真实密钥和个人信息直接放进评测 fixture；使用最小化/脱敏样本。
- 给 agent 单独的短期身份，不复用个人长期管理员 token。
- Tool result 和 session 日志也做 secret redaction；导出/分享轨迹前再次扫描。
- 对外部 connector/MCP 只授权必要 workspace、仓库和动作，定期回收不用的授权。
- 依据组织政策决定哪些任务只能本地/私有环境运行；“有 API key”不代表允许传输该数据。

## MCP 与外部工具的专项检查

1. 谁维护 server，更新是否固定/可审计？
2. 它能读什么、写什么，认证 token 由谁保存？
3. 工具描述或返回内容能否被外部用户控制？
4. 写工具是否有 preview/dry-run、幂等键和资源级授权？
5. Server 被替换、离线或返回部分成功时，harness 如何停止和告警？

OAuth 解决身份授权，不自动保证工具意图安全；TLS 保护传输，不证明 server 值得信任。

## 自动化程度的选择

- **交互开发**：工作区内读写可自动，越界和外部副作用审批。
- **CI agent**：短期令牌、只访问必要仓库/检查、输出可审计，写入走 PR。
- **无人值守任务**：范围必须窄，验收与停止条件确定，失败不能自动扩大权限。
- **生产运维**：默认只读；变更使用现有发布/审批系统，不让 agent 绕过控制面。

## 安全检查清单

- 输入中是否包含不可信指令？
- 工具权限是否超过当前目标？
- 密钥是否可能进入上下文、日志或 diff？
- 写操作是否明确目标、环境和版本？
- 是否有 dry-run、测试环境、备份或回滚？
- 失败时是否停止，而不是继续尝试更宽权限？
- 完成后能否回答“谁在何时让什么改变了”？

## 事件响应

若怀疑 agent 越权、泄密或遭 prompt injection：

1. 停止相关 session/automation，阻止继续产生副作用。
2. 撤销或轮换暴露的 token，暂停相关 MCP/extension。
3. 保存必要的审计证据，但对分享副本脱敏；记录受影响资源和时间窗。
4. 检查外部系统的实际状态，不以 agent 最终摘要代替取证。
5. 从可信 Git/备份恢复，修复权限、工具或指令边界。
6. 把最小化失败案例加入安全回归集，再恢复自动化。

有真实人员、财务、生产或合规影响时，按组织事件响应流程升级，不让 agent 自行决定通知范围。

安全配置也要纳入[评测实验室](/practice/evaluation)：测量拒绝危险动作、在权限不足时找到安全替代路径、以及不泄露模拟秘密的能力。
