# 指令与扩展层

Agent 环境通常提供多种定制机制。正确选择比把一切写进一个巨型说明文件更重要。

## 选择最小合适层

| 需求 | 合适层 | 理由 |
| --- | --- | --- |
| 只对当前任务有效 | 当前提示/计划 | 任务结束即可丢弃 |
| 每次在此仓库都遵守 | 项目指令文件 | 可版本控制，随仓库分发 |
| 特定目录有不同约定 | 嵌套指令/override | 就近覆盖，减少全局噪声 |
| 可重复但非每次需要 | Skill/命令模板 | 按需加载，保留完整流程 |
| 必须机械执行 | Hook/CI/策略引擎 | 模型指令是建议，代码规则可强制 |
| 需要实时外部数据/动作 | MCP、CLI、connector | 数据保持新鲜并可授权 |
| 需要改变循环、工具或 UI | Extension/插件 | 超出文字指令的能力范围 |
| 需要隔离调查或专业角色 | Subagent/独立会话 | 隔离上下文与工具权限 |

## 持久指令怎么写

有效指令优先写模型无法可靠推断、且会反复影响结果的内容：

- 项目如何构建、测试和格式化；
- 目录职责与应优先查看的入口；
- 与默认习惯不同的代码规范；
- 绝不能修改的文件或外部系统；
- 完成任务必须提供哪些验证证据。

删除“写高质量代码”“认真思考”等不可测试的口号。每条规则都问：若删掉它，是否能观察到更高的错误率？不能就不应常驻上下文。

## 指令优先级与冲突

具体顺序依产品而异，但通常系统/平台策略高于项目和用户内容；更具体的目录规则可能覆盖仓库规则。不要依赖模型自行调和隐含冲突：为规则标明作用域，使用 override 机制，并通过“列出已加载指令与冲突”进行验证。

## Skill 的边界

Skill 适合封装“什么时候触发、输入是什么、按什么步骤、输出与验证是什么”。它不应偷偷扩大权限，也不应把长期认证信息写入文件。需要外部系统时，让 skill 编排一个有清晰授权的 CLI/MCP 工具。

## Hook 的边界

Hook 适合格式化、阻止禁区写入、运行快速检查、记录审计事件等确定性动作。Hook 也可能执行任意代码，必须版本控制、限制超时、处理失败，并避免让“自动修复 hook”与 agent 互相无限触发。

## 配置漂移

模型、harness 与插件升级可能让旧指令失效。把定制当作代码维护：记录版本、设置最小回归任务、定期删除无用规则、对错误修复增加测试。不要仅凭“配置文件存在”判断它实际被加载。
