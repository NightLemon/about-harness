# 指令、自动化与门禁

Agent 环境通常同时提供项目指令、Skill、Hook、工具策略和 CI。它们并不是同一种“更强提示词”：指令影响模型判断，自动化执行确定性步骤，门禁则有权阻止状态变化。选错层会产生两个相反问题——只写文字却以为规则已被强制，或把每个低风险动作都变成昂贵审批。

## 先按控制强度排队

同一句“不要这样做”，落在不同层时强度完全不同：

```text
知识与建议       指令 / Skill
确定性默认       formatter / generator / safe default
输入拒绝         schema / runtime contract
动作拒绝         policy / sandbox / scoped credential
风险确认         approval / human review
结果拒绝         validator / CI / deployment gate
```

这不是从弱到强一律升级的阶梯。每层回答的问题不同：schema 能拒绝无效参数，却不能阻止另一个程序绕过它直接写文件；sandbox 能限制技术可达范围，却不能判断文章内容是否准确；CI 能拒绝不合格 commit，却通常不能撤回已经在检查前发生的外部副作用。

设计规则时先写出希望改变的状态。如果目标是“帮助 Agent 找到权威测试命令”，项目指令足够；如果目标是“任何进程都不能读取某个目录”，需要执行环境隔离；如果目标是“页面缺少来源不能发布”，需要可判定的内容契约和发布门禁。不要用较弱层的名字暗示较强保证。

## 先分清八个层次

| 需求 | 最小合适层 | 不应误认为 |
| --- | --- | --- |
| 只对当前任务有效 | 当前 Task（任务契约）或提示 | 仓库永久规范 |
| 每次在此仓库都遵守 | 项目指令文件 | 已由运行时强制 |
| 特定目录有不同约定 | 嵌套指令或 override（覆盖规则） | 对整个仓库生效 |
| 可重复但不是每次需要 | Skill（按需工作流）或命令模板 | 新的执行权限 |
| 提交前自动格式化/检查 | Hook（钩子） | 完整 CI 或安全沙箱 |
| 必须拒绝坏状态 | Schema、policy（策略）或 CI 门禁 | 模型会自觉遵守的建议 |
| 读取实时数据或产生动作 | CLI、MCP 或 connector（连接器） | 数据源自动可信、动作自动获权 |
| 改变循环、工具或界面 | Extension/plugin（扩展或插件） | 普通文字配置 |

Subagent（子智能体）或独立会话用于隔离上下文、并行调查或专业角色，不应用来规避权限、预算和验收。拆出更多角色也不会自动提高正确性；每个子任务仍需输入、输出、停止条件和归并责任。

## 用一条要求看清各层责任

以“公开结果不能包含 credential（凭据）”为例，只写一句项目指令仍不够：

| 层 | 可以承担的责任 | 失败时留下什么证据 |
| --- | --- | --- |
| 项目指令 | 告诉 Agent 不要读取、复制或提交真实凭据 | 实际加载的指令来源与 hash |
| 工具设计 | 默认不返回敏感字段，输出只包含必要数据 | ToolResult schema 与脱敏事件 |
| 权限/沙箱 | 让进程技术上无法访问无关凭据目录 | 拒绝事件、目标资源与策略版本 |
| Result serializer | 只接受允许的字段和 artifact 格式 | schema 错误与被拒字段路径 |
| Secret checker | 在候选公开产物中匹配高置信泄漏 | 文件、规则 ID 与合成负例结果 |
| 人工复核 | 处理上下文泄漏、商业敏感和规则无法表达的语义 | reviewer 决定与未决项 |

这些层互相补充，不能互相冒充。Secret checker 没命中不证明进程从未读取 Secret；sandbox 拒绝敏感目录也不证明模型不会把提示中已有的隐私写入结果；人工说“看起来没问题”也不能替代可重复扫描。

同理，“修改后必须通过测试”至少包含三件不同的事：指令告诉 Agent 运行哪条命令，执行器实际运行它，验证器 再决定这组测试是否足以支持完成。日志里只有一句“tests passed”而没有命令、退出码和环境身份，不能证明其中任何一项。

## 什么值得写进项目指令

持久指令占用每次任务的上下文，应优先保存模型无法从仓库可靠推断、且反复影响结果的信息：

- 构建、测试、格式化的权威命令；
- 目录职责、首选入口和生成文件边界；
- 与语言默认习惯不同的项目约定；
- 允许与禁止的修改、数据和外部系统；
- 完成任务必须报告的验证证据。

一条好规则应同时回答动作、作用域和可观察结果。例如：

```md
- 修改 Markdown 或站点配置后，运行 `npm run check`。
- 不编辑 `generated/`；修改其源 schema 后运行 `npm run generate`。
- 完成时列出实际执行的命令及退出码，不把静态检查称为运行时验证。
```

“认真思考”“写高质量代码”“永远使用最佳实践”没有可判定结果，只会消耗注意力。每条常驻规则都问三个问题：删掉后会重复出现哪类错误？仓库能否观察到它？更低成本的默认值或工具设计能否直接消除问题？三个问题都答不清时，先删除而不是加粗。

### 一条可维护规则的结构

把规则写成四元组，比堆叠语气词更有效：

```text
scope      对哪些路径、任务或数据生效
trigger    什么变化或动作触发
action     应执行、拒绝或报告什么
evidence   怎样观察规则确实生效
```

例如：

```md
- Scope：修改 `docs/**` 或站点配置。
- Trigger：准备结束本次修改。
- Action：依次运行 `npm run check`、`npm run facts:check`、`npm run pages:check`。
- Evidence：报告每条命令的退出码；任一失败时不声称完成。
```

规则还应说明例外由谁决定。若“紧急情况可跳过”没有主体、条件和补验证时间，它等于给所有失败留了无审计旁路。相反，低风险建议无需伪装成绝对禁令，可以明确写成“默认”“优先”或“仅在……时”。

### 记录 effective instructions

effective instructions（实际生效指令）是当前 Task（任务） 最终看到的有序规则集合，不等于仓库根目录某一个文件。一次可复现实验至少记录：

```text
task prompt identity
repository root / cwd / target paths
instruction sources in resolved order
source commit or content hash
conflict resolution
harness and surface version
```

目录继承、用户级配置和产品默认值怎样组合属于具体 Harness 行为。跨 Harness 迁移时保存的是规则意图、作用域和冲突结果，不要假定另一个产品会按同样文件名或优先级加载。

## 从建议升级为硬门禁

硬门禁适合保护明确、重要且可机械判定的不变量，例如 schema 无效、Secret 进入公开产物、测试失败或构建产物缺失。不要仅因为“这件事很重要”就写 checker；主观内容质量、架构权衡和事实解释通常仍需评审。

新增门禁前记录一张最小决策卡：

| 问题 | 必须有的答案 |
| --- | --- |
| 它阻止哪个已发生或可复现的失败？ | 一个具体坏样例，而非抽象担忧 |
| 判断是否确定？ | 输入、oracle（判定标准）和失败信息 |
| 错误拒绝的代价是什么？ | 等待时间、人工介入、绕行风险 |
| 能否自动安全修复？ | 仅机械格式问题可考虑；语义问题应给诊断 |
| 谁维护、何时删除？ | owner、版本边界或复审日期 |

门禁必须有 negative test（负例测试）：构造应被拒绝的最小输入，确认 checker 非零退出并说明原因；同时保留应通过的正例，防止规则退化成“什么都拦”。如果门禁长期没有命中、错误拒绝频繁、只检查表面关键词或失败后不给修复路径，它可能比被防止的问题更昂贵。

### 一个完整门禁至少有七个部件

| 部件 | 要回答的问题 | 缺失后的典型问题 |
| --- | --- | --- |
| Scope（范围） | 扫描哪些文件、事件或状态？ | 漏扫生成物，或误扫缓存/私人数据 |
| Predicate（谓词） | 哪个精确条件必须成立？ | “高质量”被写成不可执行口号 |
| Oracle（判定标准） | 正确答案来自 schema、测试还是来源记录？ | checker 自己发明真相 |
| Diagnostic（诊断） | 失败时指出对象、原因和修复路径吗？ | 只能反复重跑猜原因 |
| Positive/negative tests | 好样例能过、坏样例能被拒绝吗？ | 恒真或恒假的门禁仍显示绿色 |
| Cost budget（成本预算） | P50/P90 时长、资源和错误拒绝率可接受吗？ | 小改动被昂贵全量检查拖慢 |
| Lifecycle（生命周期） | 谁维护，何时复审、降级或删除？ | 历史临时约束永久累积 |

门禁的测试不应只验证错误字符串存在。负例测试应同时断言非零退出和预期诊断；正例应覆盖合法边界值。若 checker 具有自动修复能力，还要验证第二次运行不再改动，即满足幂等。

### 硬门禁、软告警与定期监测

不是所有重要问题都适合阻断每一次提交：

| 机制 | 适合的问题 | 例子 | 失败后的行为 |
| --- | --- | --- | --- |
| 本地快速检查 | 高频、确定、低成本 | 格式、schema、局部单测 | 立即修复再继续 |
| PR 硬门禁 | 合并后代价高、判定稳定 | 构建失败、高置信 Secret、契约负例 | 阻止合并 |
| 发布门禁 | 只影响可部署产物 | base path、页面资源、部署权限 | 阻止发布，不必阻止无关研究分支 |
| Soft warning（软告警） | 需要判断或允许短期例外 | 内容重复、性能趋势、低置信扫描 | 显示证据，由 owner 决定 |
| Scheduled monitor（定期监测） | 随时间或外部状态变化 | 链接可达性、产品事实新鲜度 | 建 issue/报告，不重跑每个本地编辑 |
| 人工 review | 语义、取舍和责任判断 | 内容深度、架构、证据外推 | reviewer 明确接受、退回或留未决 |

判断标准不是“问题听起来严不严重”，而是失败是否可机械判定、合并后恢复成本、检查延迟以及错误拒绝的损失。一个低置信关键词扫描即使保护安全，也更适合作为诊断信号；一个确定的凭据格式加合成 canary（探测样例）才更适合硬失败。

### 计算门禁的净价值

可以用一张简单账本做决策，不必假装所有因素都有精确货币值：

```text
avoided loss  = 命中频率 × 每次真实缺陷的恢复成本
gate cost     = 每次运行成本 × 运行频率
               + 错误拒绝频率 × 排查成本
               + 维护与升级成本
net value     = avoided loss - gate cost
```

这不是用低频为删除安全检查辩护。某些灾难性风险命中很少，仍值得用低成本确定性门禁保护。它要求把“为什么存在”写清：如果既没有历史失败、没有可信威胁模型，也没有便宜准确的判定方式，就先保留为 review checklist 或实验，不要直接放进主路径。

门禁延迟也有结构成本。把所有检查串进每次保存会打断学习；把相互独立且没有共享输出的检查并行可以缩短墙钟；但会写同一 build/cache 目录的命令不能盲目并行。并行策略本身也要作为实现契约测试。

### 识别低价值门禁

出现以下信号时，应优先降级或删除：

- 用字数、关键词数量、标题名称代替语义质量；
- 为了通过检查，作者会自然加入没有信息量的填充文本；
- 只验证“文件存在”，不验证消费者能读取或使用；
- 与另一个 checker 检查同一谓词，却有不同错误和例外；
- 检查依赖易变产品文案，但没有版本、日期或更新机制；
- 失败无法定位到具体输入，只能让人重跑全部流程；
- 长期只制造错误拒绝，从未捕获设计目标中的缺陷；
- 已有更靠近副作用边界、成本更低的控制可以替代。

删除门禁前先把它曾保护的坏样例保存下来，确认替代控制能拒绝；如果问题已经不存在，记录原因和删除 commit。不要仅注释掉 CI 行而保留一套无人运行、仍被文档声称有效的脚本。

## 授权点不要铺满工作流

授权保护的是副作用边界，不是每一步思考。对于用户已经要求的、限定在工作区内、可由 diff 回看且容易恢复的编辑，通常可以连续完成调查、修改和本地验证；逐文件、逐命令确认只会制造 approval fatigue（审批疲劳）。

应停下确认的是目标或风险发生实质变化，例如从本地编辑扩大到公开发布，从只读数据扩大到外发内容，从现有依赖扩大到新增付费服务，或从可恢复更新变成不可逆删除。能用 sandbox（沙箱）、临时 worktree（工作树）、dry-run（试运行）、资源级权限和幂等键限制风险时，优先先缩小能力，再决定是否需要人工确认。更完整的授权模型见[人类控制](/foundations/human-control)。

## 指令优先级与冲突

优先级和目录继承规则属于具体 harness 的产品行为，不能假设所有工具相同。仓库规则应显式写作用域；嵌套规则只覆盖需要变化的部分；同层规则避免同时出现“必须自动提交”和“不得提交”这类不可满足组合。

验证时不要只确认文件存在。启动一个最小任务，让 agent 报告实际加载的指令来源和冲突，再观察行为是否采用目标命令、遵守禁区并给出所需证据。若产品不支持显示加载来源，就设计一个无副作用探针，例如在临时目录放置不同的格式约定，检查输出而不触碰主工作树。

冲突处理要区分“更具体”和“更高优先级”。子目录规则可能只对目标路径更具体，但不应覆盖系统级安全边界；用户在当前 任务 中改变目标，也不自动授权新的外部副作用。无法同时满足的规则应显式报冲突，不能悄悄选择最方便的一条。

网页、issue、代码注释、测试 fixture 和 ToolResult（工具结果） 都可能出现命令式文字。除非 Harness 明确把它们装载为可信指令来源，它们只是 data（数据）。把不可信正文和项目指令拼成同一段无来源文本，会让优先级在上下文中丢失。更多来源标记、选择和注入边界见[上下文工程](/foundations/context)。

调试指令未生效时，保存实际 任务、cwd、目标路径和已加载来源，不要只反复改措辞。模型没有采用某条规则，可能是未加载、被更高层覆盖、上下文截断、规则冲突或执行能力不足；“模型不听话”只是最后的现象，不是根因分类。

## Skill、Hook 和插件的责任边界

Skill 适合封装触发条件、输入、步骤、产物与验证。它可以调用已存在的工具，但不能通过文字自行扩大工具权限，也不应保存长期 credential（凭据）。流程只用一次、步骤很短或项目代码已经能直接表达时，不必为它创建 Skill。

Hook 适合快速格式化、阻止明确禁区写入、运行小检查或记录审计事件。Hook 可能执行任意代码，因此要版本控制、固定依赖、限制超时、避免读取 Secret，并定义失败是阻断还是告警。自动修复 Hook 必须保证幂等，避免“agent 修改—Hook 改回—agent 再修改”的循环。

插件和 MCP server 会改变可发现能力与信任边界。安装前审查来源、版本、更新渠道、工具 schema、网络与数据去向；升级后比较 capability snapshot（能力快照）。详细方法见[扩展点](/implementation/extensions)。

## 维护、失败与回滚

模型、harness、插件和仓库结构升级都可能让旧指令失效。把定制当作代码维护：小步提交，记录命中的真实问题，为高价值规则保留回归样例，定期删除重复、过期和永不触发的条目。

修改后至少做三项验证：在目标目录运行正例任务；用临时 fixture 运行一个应失败的负例；确认失败发生在预期层且没有产生副作用。若成功率下降、延迟明显增加或出现错误阻断，先回滚本次指令/Hook/门禁提交，恢复上一版基线，再用单变量实验区分是规则内容、加载顺序还是实现缺陷。不要通过关闭所有安全边界来“证明”新配置更快。

### 门禁生命周期记录

每个重要门禁可以维护一条轻量记录：

```text
gate_id / owner / protected invariant
trigger and scope
positive + negative fixture
last real defect caught
runtime p50/p90 / false-positive notes
dependencies and shared output
review date / retirement condition
```

新增时先观察；判定稳定后再从 warning 升为阻断。规则发生错误拒绝时先修诊断或缩小范围，不能让作者通过添加无意义文本绕过。删除后继续观察原坏样例是否由替代控制覆盖；如果没有替代且风险仍存在，应明确接受 residual risk（剩余风险），而不是假装问题消失。

## 从症状定位责任层

| 症状 | 首查层 | 常见根因 | 不要先做什么 |
| --- | --- | --- | --- |
| Agent 没运行权威命令 | 指令发现与 Task | cwd 错、规则没加载、作用域不匹配 | 立刻加 CI 关键词检查 |
| 命令运行了但坏状态仍通过 | checker/oracle | 谓词漏项、负例不足、消费者未接线 | 把提示词写得更强硬 |
| 合法内容被拒绝 | scope/diagnostic | 正则过宽、版本漂移、语义被关键词代理 | 让作者添加无意义文本 |
| Deny 后仍发生外部写入 | 工具/policy/sandbox | 另一路径绕过、检查发生在副作用后 | 只修改项目说明 |
| Approval 次数过多 | 授权粒度 | 资源范围过宽、可逆动作也逐步询问 | 关闭所有批准 |
| 本地通过而 CI 失败 | 环境与身份 | runtime、lock、OS、base path 或缓存差异 | 无证据重跑直到偶然绿色 |
| 门禁长期无人维护 | lifecycle | owner 缺失、原风险消失、重复检查 | 继续追加例外 |

定位时保存第一处失败，不要让后续连锁错误掩盖根因。先复现最小输入，再判断应该修规则、修实现、调整触发频率还是删除门禁。
