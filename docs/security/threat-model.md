# Agent Harness 威胁模型

Threat model（威胁模型）不是一张“可能被攻击”的清单，而是对系统边界、资产、攻击者能力、失败后果和控制证据的结构化假设。Agent harness 的特殊之处在于：模型会读取不可信内容、生成下一步动作，并借工具触达文件、网络和外部账号。因此“模型是否听话”不是安全边界，控制必须落在模型无法绕过的执行层。

## 先确定范围与安全目标

第一句话写清所建模的系统，例如：

> 本模型覆盖 coding agent 从接收仓库任务、调用模型与本地工具、生成补丁到运行测试的过程；不覆盖补丁合并后的生产部署。

范围同时列出入口、出口、环境和不包含项。没有边界时，“保护所有数据免受所有风险”无法验证。对范围内系统定义具体安全目标：

- **Confidentiality（机密性）**：凭据、私有代码和个人数据不流向未授权接收方；
- **Integrity（完整性）**：任务、策略、代码、评测输入和发布产物不被未授权篡改；
- **Availability（可用性）**：循环能在预算内停止，关键恢复路径仍可用；
- **Authorization（授权）**：动作使用发起者实际授予的最小权限，不把“能访问”误作“允许使用”；
- **Accountability（可追责性）**：能够回答谁在何时基于什么输入让什么资源发生了变化；
- **Recoverability（可恢复性）**：失败可以隔离、回退并验证没有重复副作用。

安全目标彼此不能替代。加密传输保护机密性，却不证明接收方有权获得数据；审计记录能检测事件，却不阻止破坏性写入。

## 画系统与信任边界

先画数据流，不要从威胁名称开始。一个常见 harness 至少包含：

```text
用户/调度器
   │ task + authority
   ▼
Harness controller ── prompt/context ──► Model provider
   │                                      │ model output
   │ policy decision                      ▼
   ├──────────────► Tool registry / MCP servers
   │                    ├─ workspace / shell / browser
   │                    └─ Git / issue / message / production APIs
   │
   └──────────────► trace / memory / artifact / telemetry
```

每条箭头记录：数据类别、发送方、接收方、认证身份、允许目的、保留时间、失败行为和谁能修改返回内容。信任边界出现在权限、管理主体或数据分类发生变化的地方，不只出现在网络边缘。

需要显式区分：

- 用户指令与仓库/网页/文档中的文字；
- harness controller 与概率模型；
- 本地可信代码与第三方 dependency、skill、extension、MCP server；
- 只读查询、工作区写入和外部不可逆副作用；
- 测试、staging 与 production 身份；
- 当前 run、跨会话 memory 和公开 artifact；
- 控制平面中的 policy/config 与数据平面中的模型/工具输入输出。

来源可信度与动作授权是两条独立轴。官方文档可以是高可信事实来源，但不能自行授权发布；用户上传的任务可能获得明确授权，但其中嵌入的网页内容仍不可信。

## 资产要和损害配对

资产不是只有 secret。列出资产、所有者、位置、价值、允许接收方和最坏损害：

| 资产 | 典型位置 | 主要损害 |
| --- | --- | --- |
| 源码与 Git 历史 | workspace、remote、patch | 篡改、知识产权泄漏、错误归因 |
| 凭据与浏览器 session | secret store、进程环境、cookie jar | 账号接管、横向移动、费用损失 |
| 用户/客户数据 | prompt、tool result、trace、索引 | 隐私泄漏、跨租户暴露、违规保留 |
| 工具与策略配置 | registry、allowlist、approval rule | 越权执行、边界静默扩大 |
| 模型上下文与 memory | session、向量库、checkpoint | 指令污染、跨任务数据串联 |
| 运行环境 | shell、container、runner、宿主挂载 | 任意执行、持久化、影响其他任务 |
| 外部资源 | issue、消息、云资源、数据库 | 误发、重复写、删除、生产中断 |
| 预算与容量 | token、费用、CPU、并发配额 | 资源耗尽、拒绝服务、账单异常 |
| Trace 与评测结果 | artifact、日志、公开站点 | 敏感数据复制、虚假结论、取证失真 |

“泄露一段代码”和“泄露部署密钥”的严重性不同；“改错本地临时文件”和“强推受保护分支”的可恢复性也不同。风险优先级必须结合具体后果。

## 谁或什么会造成威胁

不要把攻击者简化成“恶意模型”。记录每类主体能控制什么、不能控制什么：

- 外部网页、issue、PDF 或代码贡献者可以控制模型读取的数据；
- 恶意或被攻陷的 dependency/MCP server 可以控制工具描述、返回值或执行代码；
- 获得低权限账号的人可能诱导 agent 代为使用更高权限工具，形成 confused deputy（混淆代理）；
- 正常用户可能误指定 production、粘贴凭据或批准了没有看懂的动作；
- 模型与 parser 可能在没有恶意者时产生错误 action、无限循环或 schema 偏差；
- 并发 run 可能争用同一工作区、缓存、幂等键或外部资源；
- Provider、网络和工具故障可能返回部分成功，让重试制造重复副作用。

同时写出能力限制。例如网页攻击者能控制页面文本但不能直接调用 shell；真正的风险是模型把文本转换成工具 action 后，controller 是否执行。这能把缓解点定位到动作边界。

## 用可验证句子描述威胁

推荐模板：

```text
当【主体】通过【入口】控制【数据/状态】时，
它可能跨越【信任边界】，借助【工具或身份】执行【动作】，
导致【资产与具体损害】；现有【控制】在【条件】下可能失效。
```

例如：

> 仓库贡献者通过代码注释控制模型上下文，诱导 agent 调用已授权的 issue 工具发送进程环境；若发送策略只检查域名、不检查字段来源，私有凭据可能离开本机。

“模型可能犯错”没有入口、边界和损害，无法选择控制；“Prompt injection”只有类别名，也还不是完整威胁场景。

## Agent 特有威胁目录

目录用于查漏，不替代具体场景：

| 类别 | 场景 | 应优先验证的边界 |
| --- | --- | --- |
| 指令完整性 | 网页、注释、tool output 或 memory 冒充高优先级指令 | 来源标签、指令/数据分离、目标漂移检测 |
| 权限提升 | 低权限任务借 agent 的高权限身份操作外部系统 | 每次动作的主体、资源、目的与权限 |
| 工具组合外发 | 一个工具读 secret，另一个工具发送内容 | 跨工具信息流与参数 policy |
| 参数/命令注入 | 不可信分支名、路径或 URL 进入 shell 字符串 | 结构化参数、路径/域 allowlist、无 shell 拼接 |
| 路径与租户逃逸 | `..`、符号链接、错误 namespace 越过工作区/租户 | 规范化后的真实路径和资源级鉴权 |
| 副作用重放 | timeout/部分成功后重试创建两次资源 | 幂等键、结果查询、补偿与重试上限 |
| Memory/fixture poisoning | 攻击内容跨 run 持久化或污染评测答案 | 写入审批、来源、TTL、隔离与版本 hash |
| 状态混淆 | checkpoint 与新 config/task 不匹配 | 身份绑定、计数延续和恢复校验 |
| 资源耗尽 | 无限工具循环、大输出、递归委派、费用放大 | steps/token/cost/并发预算和取消传播 |
| 供应链替换 | extension、MCP、Action、镜像或 lock 被替换 | 固定版本、来源审查、最小权限和隔离更新 |
| 观察面泄漏 | prompt、tool args、stdout、截图进入 trace/遥测 | 采集前最小化、脱敏、访问和删除 |
| 不可恢复变更 | 删除、发布、支付、通知或强推无法撤销 | preview、动作时审批、备份与双阶段提交 |

要特别检查控制组合。单个工具都“合法”不代表组合安全；读取仓库和发送消息各自合理，组合后可能成为外发通道。Sandbox 只限制计算环境，也不一定限制已授权 API 的逻辑越权。

## 风险排序不需要伪精确分数

对每个场景记录四个维度：发生可能性、影响、影响范围和恢复难度。使用 `low/medium/high` 也可以，但每档必须有定义和证据。例如：

- **影响 high**：可触达 production、长期凭据、多租户数据或不可逆外部动作；
- **范围 high**：一个成功输入能影响多个用户、仓库或后续 run；
- **恢复难**：无法确认副作用、没有备份、必须通知外部人员或历史不可完整清除。

把高影响且难恢复的威胁优先改成 fail-closed（失败关闭），即不确定时拒绝或停止。不要用 `likelihood × impact = 12` 这类数字制造客观感，除非每个尺度和数据来源都已定义。

风险排序还要写置信度。缺工具权限清单、网络日志或 provider 保留策略时，结论是“未知”，不是低风险。未知高影响边界应先调查或限制能力。

## 控制要覆盖完整事故链

每个高优先级威胁至少映射四类控制：

1. **预防**：最小工具、短期身份、sandbox、资源级 allowlist、结构化 schema、默认禁网；
2. **检测**：policy decision、目标漂移、异常费用、secret scan、工具清单 diff、外部状态核对；
3. **遏制**：取消传播、并发/费用上限、关闭出口、吊销句柄、隔离 artifact；
4. **恢复**：幂等重试、checkpoint、备份、补偿动作、凭据轮换和固定回归。

有效控制通常具备：在模型之外强制；默认拒绝；作用于规范化后的真实资源；与 task/run/identity 绑定；失败可观察；不能被同一被保护输入修改。只写“提示模型不要泄漏”或“让第二个模型审核”属于概率性缓解，不是硬边界。

Approval（审批）与 sandbox 解决不同问题：审批确认人是否同意具体副作用；sandbox 限制即使获批的代码能触达什么。审批文本必须展示最终目标、账号、数据、变化与可撤销性，并在执行前重新验证，避免审批后参数被替换的 time-of-check/time-of-use（检查与使用时序）问题。

## 为每项控制定义证据

威胁模型不是控制存在性表格，而是控制有效性的测试计划：

| 控制 | 正例 | 负例 | 故障注入 | 恢复断言 |
| --- | --- | --- | --- | --- |
| 工具 allowlist | 允许任务内只读工具 | 未列工具在 handler 前被拒绝 | registry 缺失工具 | run 明确停止且无副作用 |
| 域 allowlist | 访问本地允许域 | 外域与重定向被拒绝 | DNS/连接部分失败 | 不重试到更宽域 |
| 幂等键 | 首次写入成功 | 同键重复不再写 | 响应丢失但服务已提交 | 查询状态而非盲目重放 |
| 预算 | 正常任务完成 | 无限 action 到上限停止 | adapter 阻塞 | timeout/cancel 后子任务退出 |
| 脱敏 | 合成数据可记录 | canary secret/个人路径被拒绝 | 编码或嵌套字段 | 隔离 artifact 并保留脱敏证据 |

测试应断言控制发生的顺序。例如越权工具必须在 handler 执行前被 policy 拒绝；只看最终“没有数据泄漏”可能漏掉工具已调用但恰好失败。攻击 fixture 使用合成 canary，不放真实凭据或真实客户内容。

## 工作例：读取仓库并生成补丁

### 范围和流

输入是用户任务与本地仓库；agent 可以读取工作区、生成补丁并运行预定义测试，不可访问个人主目录、环境凭据、网络或 Git remote。输出是工作区 diff、测试结果和脱敏 trace。

### 关键威胁与控制

| 威胁 | 预防 | 检测/停止 | 恢复 | 残余风险 |
| --- | --- | --- | --- | --- |
| 恶意注释要求外发环境变量 | 不提供环境读取和网络发送组合；参数过滤敏感键 | `policy_denied` 后停止 | 撤销意外暴露凭据 | 模型仍可能把秘密编码进允许输出 |
| 路径逃逸写到仓库外 | 解析真实路径并限制 workspace root | 记录拒绝目标，不尝试扩大权限 | 删除隔离临时文件 | 链接/挂载行为依赖 OS |
| 测试命令产生破坏性副作用 | 固定命令/容器、禁网、短期环境 | timeout、进程树取消、资源上限 | 恢复干净 worktree | 依赖安装脚本仍属供应链风险 |
| timeout 后重复写外部资源 | 本范围没有外部写工具 | 检测未知副作用并停止 | 从已知 checkpoint 重放只读步骤 | 将来增加外部工具需重新建模 |

### 验收

成功不仅是补丁通过测试，还包括：只改允许路径、未使用未授权工具、拒绝事件可见、trace 不含凭据、取消能传播、失败可恢复。这个例子的最大残余风险是被允许的源码输出本身可能包含敏感业务数据，因此公开 diff 前仍需人工复核。

## 威胁模型何时失效

以下变化触发重新建模，而不是只改风险表日期：

- 新模型/provider、远程执行 surface 或浏览器登录态；
- 新工具、MCP server、extension、skill 或自动授权；
- 文件、网络、Git、消息、支付或 production 权限扩大；
- Memory、RAG、trace、遥测或跨租户数据流变化；
- 新自动化、并发/委派拓扑或无人值守运行；
- 依赖、runner、部署链和身份系统升级；
- 真实事故、near miss（险情）或控制负例失效。

每条威胁记录 owner、最近复核、控制、测试、残余风险和接受者。接受残余风险是具体负责人对具体范围的决策，不是“暂时没时间”的同义词。范围或假设改变后，旧接受结论自动失效。

## 在本项目验证部分控制

### 前置条件与固定输入

要求 Python 3.11+、uv 0.11、Node.js 22+，依赖已按锁文件安装，并从仓库根目录执行。测试只使用 fake/replay 和 `lab.local` 合成 fixture，不需要凭据、真实浏览器、网络或付费 API。

### 命令

```powershell
uv run --frozen --offline pytest -q lab/tests/test_loop.py
npm run labs:all
npm run secrets:check
```

### 预期输出与安全断言

Loop 测试应有 13 项通过，并证明：未授权工具在 handler 前停止；步骤与模型调用预算能打断循环；timeout/cancel 有明确停止原因；幂等键避免重复工具副作用；checkpoint 恢复保留状态；未通过验收或迟到 validator 结果不能成为 completed。六个 lab 应全部 `passed=true`、`offline=true`、`negative_rejected=true`、`safety_violation=false`。

浏览器负例特别断言：包含注入文本的本地页面仍只抽取两条目录记录，外部域导航被拒绝，`side_effects=0`。Secret scan 应报告候选文件均未命中当前已知凭据和个人路径模式。

### 失败、停止、清理与回退

若危险 handler 被执行、外域请求发生、secret 出现在 trace、取消后子任务仍运行，立即停止；不要通过删除负例或放宽 allowlist 让测试通过。先隔离输出、撤销任何可能暴露的测试凭据，再修 controller/policy 边界。

命令只使用本地固定输入并可能产生可忽略测试缓存；需要时只清理 `.pytest_cache/`。误改 fixture 或策略时先用 `git diff -- lab/` 定位，只恢复自己本轮改动。若新控制破坏正常路径，回到上一已验证 policy/config，再保留失败样例用于修复。

这些 E1 测试只证明固定实现和合成威胁能触发预期控制，不证明真实浏览器、MCP、provider、操作系统隔离或生产身份安全。未覆盖项必须保留为 residual risk（残余风险）。

下一步使用[Agent 安全评审工作表](/practice/security-review)把数据流、能力、威胁、控制负例和事件 Runbook 汇总为一份可复核决定；再用[Prompt Injection](/security/prompt-injection)细化不可信内容路径，到[Secret 与隐私](/security/secrets-privacy)建立数据清单，并在[事件响应](/security/incident-response)定义控制失效后的顺序。供应链入口见[扩展与供应链](/security/supply-chain)。

## 检查题

1. 官方网页中的文字为何仍不能授权工具副作用？
2. 一个读取工具和一个发送工具分别安全，为什么组合后可能危险？
3. Approval 已通过时，sandbox 还有什么作用？
4. “测试最终没有泄漏”为什么不足以证明 policy 在正确位置阻断？
5. 新增跨会话 memory 后，威胁模型哪些边界必须重画？
