# Agent 事件响应

事件响应的目标不是让模型“自行修复”，而是在证据仍可信时停止扩散、恢复控制并建立可验证的防回归措施。

## 触发条件

Secret 或个人数据泄漏、未授权副作用、破坏性写入、供应链异常、费用失控、跨租户访问、公开结果污染或无法解释的权限提升，都应触发人工接管。预先给每类事件配置 owner、停止开关、联络渠道和恢复点。

## 固定顺序

1. 停止 run、子任务、部署和自动重试；
2. 隔离 artifact 与环境，不扩大读取范围；
3. 撤销凭据、token、session 与高风险访问；
4. 保存不含秘密的时间线、版本、trace hash、退出码和受影响范围；
5. 从已知良好 checkpoint 恢复，并验证重复副作用没有发生；
6. 修复根因，加入合成负例和检测门禁；
7. 由责任人确认残余风险后恢复自动化。

隔离优先于“删干净”：过早删除会破坏取证，继续运行又会扩大泄漏。保存 hash 与结构化事件即可，不复制真实 secret 或攻击载荷全文。

## 示例：工具外发被发现

假设浏览器 agent 尝试向非允许域发送页面数据。立即取消当前 run、关闭凭据句柄和网络出口；保存 policy decision、目标域和脱敏参数 hash。确认没有已完成请求后，从上个 checkpoint 以无网络配置重放固定 fixture。新回归应断言外域调用在模型动作之后、工具执行之前被 policy 拒绝。

## Git 与公开站点

删除工作树文件不等于清除 Git 历史或构建缓存。一旦内容已进入 remote，历史重写、通知受影响者、撤销凭据和重新部署都需要专门决策。没有相应授权时只做本地隔离、影响评估和报告，不 force push。

## 复盘检查

记录 detection gap、control 为什么未阻断、受影响数据与人员、恢复时间、残余风险和负责人。确认停止开关、撤销路径、恢复步骤与回归用例都实际演练过。下一步回到[Secret 与隐私](/security/secrets-privacy)和[供应链安全](/security/supply-chain)修正预防控制。
