# 长任务与部署：从一次调用到可恢复服务

一次同步请求结束后，业务任务不一定结束。研究可能需要多轮检索，审批可能等到明天，写操作可能已经完成却丢失回执。长任务设计首先要决定谁持有状态、谁承担恢复，以及何时能够向用户宣称完成。

本页区分稳定的部署责任和产品事实。OpenAI Agents API 的相关材料实际核对于 **2026-09-21**，证据为 E0；本仓库没有创建云会话、沙箱、队列或付费资源。

## 五种状态不要混在一起

| 对象 | 保存什么 | 单独不足以证明什么 |
| --- | --- | --- |
| 对话历史 | 用户和模型说过什么 | 外部工具动作是否已经提交 |
| Session（会话） | 交互配置和连续上下文 | 所有业务资源和审批仍有效 |
| Checkpoint（检查点） | 执行位置、输入身份、预算和待办动作 | 外部系统与本地存储原子一致 |
| 业务台账 | 写入意图、幂等键、回执与对账状态 | 模型的最终答案符合业务要求 |
| 执行环境 | 文件、进程、网络与运行依赖 | 用户身份、授权和租户隔离自动正确 |

恢复流程应重新确认版本、权限、预算和外部状态。恢复一段聊天并重新运行最后一个写操作，可能造成重复副作用；只保存最终文本也无法判断哪里能够安全继续。

## 自建、框架与托管分别少做什么

| 路径 | 控制循环与状态的方式 | 应用仍负责 |
| --- | --- | --- |
| 自建循环 + 现有队列/数据库 | 自己定义任务状态机、租约、检查点及调度 | 全部协议、部署和业务正确性 |
| 应用内框架 | 使用框架的 runner、图或工作流抽象 | 存储配置、身份、工具实现、边界测试和运维 |
| 托管 Harness 服务 | 服务方运行循环并提供会话等基础设施 | 业务工具、授权、数据规则、使用限制和最终验收 |

官方 Agents 总览把 Responses API、Agents SDK 与 Agents API 列为不同起点：直接模型接入、应用内运行时、托管 Codex Harness。[FACT:openai-runtime-options] 选择取决于你希望控制和维护哪些层，而不是哪条路径“更智能”。

## Agents API 的当前责任边界

官方概览将 agent、environment、session、events/items 作为核心概念，并描述由服务管理会话、编排、上下文压缩和恢复；执行环境可以采用服务支持的不同沙箱路径。[FACT:openai-agents-api]

这些是上游的产品声明。采用前仍要按目标版本验证：工具处理函数运行在哪里；哪些文件能被模型读到；审批绑定哪个动作；会话、沙箱和业务记录的生命周期是否独立；终止会话是否也会停止子任务与释放资源。不要把“managed”解释为免除数据责任，也不要从文档存在推断自己的账号或地区已经可用。

本地文档中的 `Session`、SDK session、Responses conversation 和托管沙箱并非可互换的资源。迁移时要做责任映射，不能只替换一个 API 名称。

## 队列、租约与事件

后台任务通常采用至少一次投递，因此消费者需要识别同一任务和重试身份。租约过期后，第二个 worker 可能开始处理；旧 worker 仍可能稍后返回。状态提交需要版本检查或 fencing token（隔离旧执行者的令牌），防止旧结果覆盖新终态。

事件和 webhook（服务向接收端推送的通知）可能延迟、重复或乱序。接收端验证签名、主体和事件身份；通知只促使重新读取权威状态，不直接把“收到了 completed 字符串”当作业务完成。轮询也需预算与退避，避免恢复机制制造更多负载。

例如写入报告后网络断开：先把状态保留为 `unknown outcome`（结果未知），使用原业务身份查询回执；确认完成则接受原结果，确认未执行且前提仍成立才按契约重试。查询不到可能源于最终一致性，不能立即解释成没发生。完整负例见[可靠性恢复工作坊](/practice/reliability-recovery)。

## 人工审批也有版本

审批应绑定主体、目标、参数或内容摘要、有效期和允许操作。用户批准“向甲发送这一版报告”，不等于批准重试时改成乙或发送新的内容。审批等待期间数据或目标变化，需要重新预览或停止；已经拒绝的动作不能由另一个 Agent 换工具绕过。

超时、取消和用户拒绝是不同终止原因。取消向下传播后，仍须处理迟到事件和已经提交的副作用；“取消请求已发送”不意味着外部执行已撤销。

## 沙箱与多租户

沙箱需要检查文件系统、进程、网络、挂载目录和凭据注入方式。Git worktree 分离工作目录，不提供操作系统权限隔离；容器也只有在权限、挂载和网络策略配置正确时才形成相应边界。

多租户隔离要覆盖存储、缓存、检索、队列、日志和恢复路径。任务 ID 难以猜测不等于访问控制；拿到旧的句柄也不应绕过当前身份与权限。公开轨迹必须脱敏，不能把内部调试信息直接变成用户可下载产物。

## 上线前如何验证

用固定任务依次制造：工作进程重启、消息重复、旧租约迟到、审批过期、写入丢回执、客户端取消、数据版本变化和租户越界。检查是否出现重复副作用、预算重置、权限扩大或假完成，并保存恢复前后的状态身份。

这些场景可先做 E1 模拟；当前仓库的[状态与可靠执行](/foundations/state-reliability)和[恢复工作坊](/practice/reliability-recovery)已经提供限定案例。它们使用内存 fake，不证明磁盘崩溃安全、真实队列、跨区域一致性或托管服务保证。

部署回退至少保留旧配置和读取历史状态的能力，停止接收新任务，再决定排空、取消或人工对账已有任务。回退代码不能撤回已发送消息或费用。下一步用[兼容性矩阵](/references/compatibility)记录目标组合中哪些责任已有证据，哪些仍是 `untested`。
