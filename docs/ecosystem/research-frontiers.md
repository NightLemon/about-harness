# Agent Harness 的研究前沿：把新方法放回可验证循环

研究前沿常用相同的词描述不同对象：模型在一次调用中花更多计算、系统搜索多个候选、训练改变参数、记忆改变未来上下文。它们都会影响 agent 行为，却处在不同控制面。先分清作用位置，才能避免把一次论文复现、一个产品开关或一次离线 replay 写成通用能力提升。

本页讨论稳定的方法结构、仍在变化的研究问题和本项目可执行的建议。它不提供当前模型、论文或产品的排名。

## 推理时计算：预算是决策，不是品质标签

推理时计算（test-time compute）指在一次任务执行时额外分配模型调用、token、搜索节点或验证次数。稳定的机制是：预算换取更多候选或更多检查机会；它同时增加延迟、费用、失败面和需要治理的副作用。它不等于“更高 reasoning 一定更正确”。

把预算写进 controller 的共享账本：每个候选、子任务、重试和 Judge 都消耗同一上限。对每一笔消耗记录目的：是为了修复确定性错误、扩大候选集，还是等待暂时性服务恢复。若任务缺少关键事实、权限或可验证的验收，增加计算只会更快地产生未经证实的答案。

反例是一个写操作超时后连续提高推理预算。这里未知的是外部副作用是否已发生，应先用 receipt 对账；更多模型调用不会把 unknown outcome 变成安全重试。

## 搜索与验证：候选多样性不等于证据

搜索（search）从同一任务生成或展开多个候选路径；验证（verification）用独立的测试、规则、人工或业务查询淘汰候选。二者必须分开记录：候选生成器可能共享偏差，验证器也可能过期或只覆盖表面结构。

一个可审计循环是：

```text
冻结 Task 与预算
  → 生成有限候选（保存 draw/plan ID）
  → 用独立 validator 取得证据
  → 聚合通过、失败与未知
  → 选择、回退或停止
```

随机重采样可带来新的候选，但不能增加独立 Task 数，也不能把 `best-of-k` 写成单次默认体验。若验证器只检查 JSON 格式，搜索到的“最佳”候选最多证明格式；如果要声称业务收益，还需要与业务 acceptance 对齐的 oracle。详细的重采样、重试和分母规则见[Judge 与人工评分](/evaluation/judges)与[指标与区间](/evaluation/metrics)。

## Agent 训练：优化目标必须暴露在运行时

Agent training（智能体训练）可以使用示范轨迹、偏好比较、环境反馈或其他信号改变模型或策略。稳定的工程问题不在于采用哪一种论文术语，而在于训练目标是否与部署验收一致：数据来源和许可是否清楚，轨迹是否含有泄漏或越权动作，奖励是否会鼓励规避验证，训练后能否在未见任务上复核。

训练集中的“完成”标签可能只表示模型输出了一个看似合理的动作。部署后仍由 harness 的 policy、sandbox、approval 和 validator 强制边界；训练不能替代它们。训练更新还应建立新 config identity，不能与旧模型、旧工具 schema 或旧评测记录混合汇总。

当前研究会继续改变具体算法和基准，所以任何产品或论文效果都应标明版本、任务、训练数据边界、harness 与评测设置。本项目建议先把不可接受的轨迹转成离线负例和回归任务，再讨论训练是否值得；这比把失败 trace 直接当作“更多数据”安全得多。

## 长期记忆与持续学习：四个对象，四条治理链

长期记忆、检索索引、经验缓存和持续学习常被统称为“记住了”，实际至少有四个不同对象：

| 对象 | 改变什么 | 主要风险 | 必要证据 |
| --- | --- | --- | --- |
| 工作记忆 | 当前 run 的可见状态 | 过期或和真实世界不一致 | checkpoint 与外部对账 |
| 长期记忆/索引 | 以后检索到的内容 | 过度授权、污染、删除失效 | 来源、scope、TTL、删除链 |
| 经验缓存 | 相似输入的复用结果 | 身份或目标漂移后错误复用 | 参数 hash、主体、版本、失效规则 |
| 参数持续学习 | 未来模型的行为分布 | 数据许可、遗忘、不可撤销影响 | 数据谱系、评测 split、回滚/替代计划 |

稳定原则是：先治理数据，再允许影响决策。一个检索命中不是事实；一段过去的成功轨迹不是当前任务的授权；一次参数更新也不是已通过安全验收。特别是参数持续学习的删除通常不能简单等同于删除一条数据库记录，因此必须在引入前明确撤回、隔离或重新训练的现实成本。

反例是把网页中的指令摘要写入长期 memory，再让它影响无关任务。问题不是“记忆检索不够聪明”，而是来源、权限和用途在写入或读取时被升级了。相关生命周期控制见[记忆的生命周期](/foundations/memory)与[Prompt Injection 防护](/security/prompt-injection)。

## 当前研究问题与项目建议

以下是研究方向，不是对任何当前产品能力的事实断言：怎样让 verifier 覆盖真实业务而不泄漏答案；怎样在长任务中分配搜索预算；怎样使训练、检索和工具使用在版本变化后仍可归因；怎样处理记忆删除与持续学习之间的张力。这些问题需要可重复任务、清晰失败分类和长期运行证据，不能靠一次 demo 回答。

对项目的建议是保守而具体的：

1. 先用 E1 固定 fixture 验证预算、策略、schema、来源与回滚边界；
2. 若要研究模型候选质量，再获得授权后做锁定身份的 E2 探针，并保存每个 draw 与独立 validator；
3. 只有任务集、holdout、安全和成本门槛齐全时，才把某种搜索、训练或记忆策略纳入 E3 采用决定；
4. 无法验证的高影响任务保留人工验收或 abstain，而不是用更多采样掩盖不确定性。

在[生态系统工作坊](/practice/ecosystem-workshop)中，可以用合成 Task 设计一张“候选—验证—选择”卡，标出预算、oracle、失败反例、记忆写入条件和停止点。这是 E0 设计练习；不训练模型、不调用 API，也不产生真实系统或基准结论。
