# 知识、检索与记忆：让信息可用而不被误信

知识系统的难点不是“能不能搜到一段文本”，而是这段文本能否在正确的 Task、权限和时间下影响正确的决定。检索增强生成（Retrieval-Augmented Generation，RAG）把外部材料在推理时加入模型上下文；长期记忆则让某些材料跨步骤或跨会话再次可见。二者都改变模型看到什么，却都不自动提供事实性、授权或业务完成证明。

本页讲稳定的工程机制。产品定位和版本敏感能力单列为 E0 事实；本仓库没有运行真实向量库、LlamaIndex、云检索或持续学习服务，因此不把任何离线实现写成它们的可用性证据。

## 一条知识路径要经过哪些边界

一个可审计的知识路径通常是：

```text
source → ingest → parse/chunk → index → retrieve → rerank
       → context budget → model proposal → validator → trace
```

每一步都可能改变结论。`source` 决定来源、许可、主体和时间；`parse/chunk` 决定表格、标题、代码和否定条件是否还在同一证据单元；`index` 只让材料可被候选检索；`retrieve` 和 `rerank` 排序候选；context builder 最终决定模型实际看见什么。模型引用了一段文本，不等于该段文本最新、完整或有权决定动作。

最小身份至少包括 `source_id`、版本或内容 hash、取得时间、许可/数据分类、owner、scope、chunk ID 和解析器版本。检索结果进入上下文时还要保留查询、过滤器、排序分数、截断状态和被省略范围。没有这些身份，之后无法区分“没有检索到”“被权限过滤”“被预算丢弃”和“模型读到后判断错误”。

## RAG 先检索，再判断是否足够

检索的目标是取回候选证据，不是直接生成答案。一个稳妥的读取顺序是：

1. 先用租户、项目、权限、有效期和数据分类做硬过滤；
2. 再按当前 Task 的问题、版本和实体取回有限候选；
3. 用 rerank（重排）比较候选和问题的相关性，同时保留来源；
4. 检查证据是否覆盖关键条件、反例和冲突；
5. 只有足够时才写入 context，否则请求澄清、继续受限检索或 abstain（弃权）。

Rerank 只能重新排序允许集合，不能把无权、过期或被删除的材料重新变成可信证据。将访问控制放在排序之后是常见错误：此时敏感内容可能已经进入 embedding、缓存、日志或模型上下文。

一个失败案例是：用户询问“当前生产保留期”，系统检索到一篇旧迁移说明和一篇现行 policy。旧说明关键词更相近，于是模型给出旧天数。这里把 top-1 分数提高不会修复问题；应在 ingest 时记录版本和生效范围，在检索前过滤 retired 文档，并要求答案引用生效 policy 的定位。若两个有效来源仍冲突，正确结果是标记冲突，不是让 reranker 选一个看起来更流畅的段落。

## Chunk、上下文压缩与证据丢失

Chunk 是检索单位，不应被当作知识的天然边界。太大时预算被少数长文占满，太小时条件、例外和引用断裂。先按文档结构、对象边界和验证需求切分，再评估是否需要重叠；重叠会提高召回，也会让同一来源多次出现并人为放大权重。

压缩是另一种有损变换。它可以减少长会话、日志或检索结果的 token，但必须保留：原始来源、版本、否定结论、权限限制、精确数值、未解决冲突和可回到原文的定位。摘要若把“尚未验证”写成“已确认”，或者把外部文本中的命令写成项目规则，问题不是摘要不够优美，而是证据和指令边界已经损坏。

建议为压缩建立保真断言：每个关键 claim 都能回到 source/chunk；每条禁止动作仍可定位；被裁掉的范围可见；冲突数量不会静默变为零。压缩失败应回到原文、缩小 Task 或提高明确预算，不能把失败摘要继续写入长期记忆。

## 长期记忆不是检索缓存的别名

长期 memory（记忆）适合存放有治理价值、能在未来复用且来源明确的记录，例如已确认的项目约束、任务结果的 artifact reference 或用户显式要求保留的偏好。它不适合自动吸收所有网页、模型总结或工具输出。

一条长期记录需要生命周期：

```text
proposed → reviewed → active → superseded/expired/quarantined → deleted
```

写入前检查来源、主体、scope、用途、敏感级别、TTL 和允许消费者；读取前再次检查当前租户、Task 和权限。更新不能覆盖历史依据：用新版本指向旧版本，并保留冲突和失效原因。删除也不是“下次搜索不显示”——索引、缓存、checkpoint、trace、备份和下游派生摘要都要有删除传播计划。

失败案例是客服摘要把 A 租户的故障根因写进共享记忆，B 租户随后检索到该摘要。即使模型没有调用外部工具，机密性已经被破坏。补一个更好的 embedding 或提高 top-k 不能修复它；记录必须在写入和读取两端带租户隔离，删除请求还要能定位所有副本和未完成的异步清理。

## 权限、删除与恢复要一起设计

知识系统常遗漏恢复路径。checkpoint 可能保存已选 chunk，缓存可能保存 rerank 结果，工作队列可能在删除请求之后才开始索引。因而删除协议应明确：哪个 ID 被删除、哪些派生物受影响、何时停止新读取、何时完成各副本清理、哪些不可立即清除的备份受保留政策约束，以及在清理前后如何审计。

恢复一个旧 checkpoint 前也要重新做权限和版本过滤。它只证明“当时看到过什么”，不证明材料现在仍可读、仍适用或仍未被删除。高影响回答应把检索身份和最终引用写入 trace；若删除或权限状态未知，停止自动回答比用旧上下文继续生成更安全。

这只能说明官方文档所述定位，不能证明本仓库已经安装、配置或验证了 LlamaIndex，也不能证明任何 connector、解析器、index、reranker 或托管服务适合当前数据。若采用它或其他同类框架，仍应把 connector、parser、index、retriever、reranker、权限过滤、模型、validator 和版本组成一个可复核 config identity。

## 工程取舍：先选失败成本，再选组件

| 选择 | 可能收益 | 主要代价 | 必须验证 |
| --- | --- | --- | --- |
| 更大 top-k | 少漏候选 | 噪声、成本、注入面增大 | 关键证据是否反而被挤出 |
| 更激进 rerank | 提高局部相关性 | 版本漂移、偏见和延迟 | 过滤是否先于排序、冲突是否保留 |
| 更短摘要 | 降低 token | 否定条件和来源丢失 | 保真断言与原文可回跳 |
| 自动写长期记忆 | 减少重复说明 | 污染、越权、删除复杂 | 写入审核、TTL、scope、删除传播 |
| 跨会话复用缓存 | 降低延迟 | 身份和版本错配 | 主体、参数 hash、失效条件 |

不要把“命中率提升”当作唯一指标。还要看带来源引用的答案正确性、冲突暴露率、权限拒绝率、删除传播时延、上下文 token、端到端延迟和人工纠正。不同 workload 的最佳取舍可能相反。

## 离线练习与下一步

做一个本页的 E0 纸上练习：给定 A 租户当前 policy v2（保存 30 天）、已过期 v1（保存 90 天）、B 租户摘要（永久保存），任务只允许使用 A 的当前资料。画出 source identity → 权限/版本过滤 → 候选 chunk → 摘要 → 记忆副本的链条；合格产物只留下 v2，注明删除 v2 时哪些派生副本需失效。若把 B 的高相关摘要排到前面或恢复 v1 结论，即为失败。只需纸笔或临时文本，无真实索引、凭据和网络；结束删除自己的草稿即可，修订失败回到三个冻结输入。此处没有自动测试；需要可执行 E1 练习时转到[生态工作坊](/practice/ecosystem-workshop)。
