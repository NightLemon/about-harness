# 模型适配卡

为每个“模型 × provider × harness × surface”组合建立一张卡。不要把同名模型在不同 provider/harness 的结果合并。

## 可复制模板

```md
# 适配卡：<model> / <provider> / <harness> / <surface>

## 身份与版本
- 模型精确 ID/快照：
- Provider/区域：
- Harness 版本与 commit：
- Surface（CLI/IDE/Desktop/Cloud）：
- 核对日期：

## 协议兼容
- 文本/流式响应：
- 单次/多次工具调用：
- 工具错误恢复：
- 上下文与输出上限的实际行为：
- reasoning/thinking 参数是否被 provider 接受并生效：
- 取消、超时、重试与 usage 元数据：

## 目标工作负载
- 任务类别与频率：
- 延迟/成本上限：
- 风险级别：
- 必须支持的语言、工具与模态：

## 能力假设
- 指令遵循：
- 工具调用与错误恢复：
- 长上下文/压缩恢复：
- 规划与验证：
- 已知弱点（附证据）：

## 探针结果
- 指令作用域：
- 检索：
- 工具恢复：
- 状态保持/压缩：
- 验证闭环：
- 安全边界：

## 当前最佳配置
- 推理强度：
- 项目指令版本：
- 工具 allowlist/schema 版本：
- Skill/extension/MCP：
- Context/compaction 策略：
- 权限/sandbox：
- 重试、超时与预算：
- 对照的默认基线/工程基线：

## 路由
- 默认处理：
- 升级到强模型/高推理的条件：
- 降级到快模型的条件：
- 必须人工审批的条件：

## 评测结果
- 任务集/commit：
- 运行次数：
- 成功率与置信说明：
- 安全违规：
- P50/P90 时长、token、成本：
- 人工纠正与失败类型：

## 结论边界
- 适用：
- 不适用/未测试：
- 下次重测触发：
```

## 示例决策（不是通用结论）

```text
组合：均衡 coding 模型 / Codex CLI / medium
默认：单仓库日常实现与调试
升级：需要跨三个服务权衡，或目标测试两次失败且根因不同
降级：只改文案、格式、固定 schema 提取
人工审批：新增生产依赖、外部发送、工作区外写入
```

卡片的价值来自失败证据和适用边界。若只有“效果很好”，它无法帮助下一次版本升级。

## 维护节奏

模型或 harness 大版本、工具 schema、项目架构、权限政策或任务分布变化时重跑核心集。每月/季度是否重测取决于变化速度；不要把固定日历当作唯一触发。

## 如何使用这张卡

先复制模板但只填写已经有证据的格子；未知项写 `untested`，不要用产品营销描述补空。第一张卡记录开箱默认，第二张记录工程基线，后续候选每次只改一个主要变量。每条“当前最佳”都要能回链任务集、配置 hash、失败 run 和停止条件。

## 常见失真

把模型 alias 当快照会混合版本；只保存最终 prompt 会遗漏项目指令与工具；只报成功率会隐藏成本与安全回退；把不同 harness 的结果合并会失去责任边界。卡片不是配置收藏夹，而是可否采用与何时回退的决策记录。

## 自检与下一步

换一位维护者，能否仅凭卡片重跑同一矩阵？模型或权限变化时，哪些结论会失效？先完成[端到端适配案例](/practice/end-to-end)，再用[评测实验室](/practice/evaluation)填入实际证据。

把卡片与[兼容性矩阵](/references/compatibility)对照，可避免把来源事实、离线职责接缝和真实运行混成一个“支持”结论。
