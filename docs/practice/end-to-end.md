# 端到端模型适配案例

本案例把前面章节串成一条完整路径。模型名、任务与数字均为**教学虚构**，不表示任何真实产品性能。

## 场景

团队想把 `acme/code-model-2026-08` 用在 Pi 的 TypeScript 单仓库中。真实工作约 60% 是小修，30% 是多文件功能/调试，10% 是只读调查。要求零模拟 secret 外传、单任务不超过 20 分钟，并尽量减少人工纠正。

候选配置只比较 thinking `low` 与 `medium`。两者共用相同模型/provider、Pi 版本、短 `AGENTS.md`、工具列表、权限边界和任务提示。

## 第 1 步：确认身份与协议

从 Pi 状态和 provider 响应记录精确 ID，不问模型自报。运行六项 smoke test：文本、单工具、多工具、参数错误恢复、取消/超时、usage 元数据。

第一次多工具测试丢失 tool call ID。团队先修 provider adapter，再继续。这一故障不记为模型能力失败，因为模型从未收到完整工具结果。

## 第 2 步：建立工程基线

项目指令只写模型无法从代码可靠推断的信息：

```md
# AGENTS.md
- Install with `npm ci`.
- Start architecture searches at `docs/architecture/index.md`.
- Fast verification: `npm run lint && npm run test -- --changed`.
- Do not edit generated files under `packages/api/generated/`.
- Finish with changed files and exact check results.
```

调查 run 只暴露 `read,grep,find,ls`；实现 run 增加 `edit,write,bash`。项目放在受限 container 中，模拟 secret 不进入真实环境变量。

## 第 3 步：跑小探针

| 探针 | 结果 | 处置 |
| --- | --- | --- |
| 指令作用域 | 两档都正确采用子目录 override | 保持配置 |
| 检索 | low 多读约 40% 文件 | 为两档都增加架构索引入口，不做单边特例 |
| 工具恢复 | adapter 修复后均能恢复 | 加入协议回归 |
| 状态保持 | low 在长日志后漏掉一个禁区 | 进入正式任务观察，不先下结论 |
| 验证 | 两档都主动复跑目标测试 | 保持配置 |
| 安全 | 均拒绝 README 内的外传诱导 | 安全任务仍保留在正式集 |

探针用于修环境和形成假设；它没有足够样本宣布 medium 更好。

## 第 4 步：设计 A/B

从历史工作抽 6 个任务：2 个小修、2 个多文件功能、2 个调试。每个任务有固定 commit、机器检查、禁止动作和 20 分钟超时。A/B 每任务各运行 3 次，共 36 次，交错顺序并使用干净 worktree。

预注册晋级条件：零安全违规；任何关键任务不退步；整体 single-run success 至少提高 5 个百分点；P90 时长增长不超过 35%。基础设施 5xx 最多重跑一次并保留原记录。

## 第 5 步：读结果而不是看总分

评测 runner 首先交来以下**错误汇总（不可用于决策）**：

| 指标 | low | medium |
| --- | ---: | ---: |
| 通过 run | 24/18? | 29/18? |
| 安全违规 | 0 | 0 |
| P50 时长 | 280 s | 330 s |
| P90 时长 | 510 s | 620 s |
| 人工纠正 | 7 | 3 |

每档只有 18 次，却写成 24/18 和 29/18。真实审阅必须先拒绝这份汇总，而不是根据漂亮百分比给结论。核对原始记录后的**修正汇总**为：

| 指标 | low | medium |
| --- | ---: | ---: |
| 通过 run | 12/18 | 15/18 |
| 安全违规 | 0 | 0 |
| P50 时长 | 280 s | 330 s |
| P90 时长 | 510 s | 620 s |
| 人工纠正 | 7 | 3 |

样本仍小，需同时查看区间和失败轨迹，不能只比较 66.7% 与 83.3%。

轨迹显示三个新增成功都来自多文件/调试，小修没有收益；medium 的 P90 增长约 22%，在预设门槛内。low 的长日志失败可通过更短工具输出改善，但改动要对两档共同重跑。

## 第 6 步：形成路由与回退

- 小修、格式、固定 schema 提取：`low`。
- 多文件功能、调试、三项以上约束：`medium`。
- 两次不同根因失败、需要架构权衡：升级到更强模型/更高预算或人工设计评审。
- 任何安全门禁失败：停止自动化，不通过重试“碰一次安全结果”。
- Provider/adapter 协议失败：回退到已验证版本，不把它算成模型判断失败。

这些结论只适用于记录的模型快照、Pi/provider 版本和任务集。把它们写进[模型适配卡](/practice/model-playbook)，而不是写成“medium 永远最好”。

## 第 7 步：固化外循环

将 adapter bug、长日志状态保持和安全诱导任务加入回归集。模型、Pi、provider adapter、工具 schema 或仓库架构升级时重跑核心集。每次真实失败先最小化和脱敏，再决定修指令、工具、harness 还是模型路由。

## 你应检查的七个证据

1. 模型身份来自可验证元数据。
2. 工具协议先于能力评测通过。
3. A/B 除一个主要变量外保持一致。
4. 每个 run 有干净起点和机器验收。
5. 安全是硬门禁，失败轨迹被保留。
6. 结论按任务类别路由，并写明未测试范围。
7. 改进进入回归集，版本变化触发重测。
