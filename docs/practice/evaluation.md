# 评测实验室

这一实践用最小成本比较两个配置。目标是学会流程，不追求发表级统计结论。

## 实验：推理强度 A/B

### 准备

选 6 个真实、可在干净分支重复的任务：2 个小修、2 个多文件实现、2 个调试。每个任务写确定性检查和禁止动作。固定模型、harness、提示、工具和仓库 commit，只比较低/中两个推理档。

### 运行矩阵

每个任务在 A、B 下各跑 3 次，共 36 run。随机打乱顺序。每个 run 使用新 worktree 或恢复 fixture，不让前一次代码和对话进入下一次。

### 记录 CSV

```csv
run_id,task_id,config,passed,safety_violation,duration_s,input_tokens,output_tokens,tool_errors,human_turns,failure_type
001,fix-01,A,1,0,93,12000,1800,0,0,
002,fix-01,B,1,0,121,14500,2300,0,0,
```

仓库根目录的 `evals/tasks.example.jsonl` 与 `evals/runs.example.jsonl` 提供 JSONL 版本的可复制样例。在项目根运行：

```bash
npm run eval:summary
```

汇总器输出每个配置的 run/任务数、通过率、Wilson 95% 区间、安全违规、P50/P90 时长、token、工具错误、人工轮次和失败类型。示例数据只演示格式，不能得出任何模型结论。

### 评分顺序

1. 任一安全违规使配置不能晋级。
2. 比较任务通过率与每类失败分布。
3. 比较 P50/P90 时长、token 和人工轮次。
4. 阅读至少全部失败轨迹，以及各配置两个成功轨迹。

比较相同任务的 A/B 配对差异，并单独列出 runner/provider 基础设施失败。轨迹可能包含源码、提示、日志和凭据；保存与分享前按[数据流与隐私](/foundations/security#数据流与隐私)处理。

### 结论格式

```text
在任务集 commit X、Harness Y vZ 上，B 的 18 次运行中通过 15 次，
A 通过 12 次；B 的中位时长高 19%，没有安全违规。
提升主要来自两个多文件任务，简单任务无明显收益。
因此复杂任务路由到 B，简单任务保留 A；未测试 UI 与外部工具任务。
```

不要写“B 模型更聪明”。

## Harness A/B

比较 harness 时固定精确模型、provider、推理强度、仓库起点和任务文本。尽可能提供职责等价的工具，但不要伪装差异：一个有内建 checkpoint，另一个没有，这本身就是要评价的 harness 特性。分别报告默认体验和经过合理调优后的体验。

## 评测 Agent 本身

若使用模型评分，给评分模型完整 rubric、匿名化候选顺序并校准它与人工样例的一致性。对安全、编译、测试和 schema 使用确定性检查。最终 scorer 不应是唯一证据，特别是它与被测模型同源时。

明确报告的是 single-run success、允许重试后的 success，还是 best-of-k。三者服务不同产品体验，不能放在同一列直接比较。


## 把生产失败变成回归

1. 脱敏并最小化失败案例。
2. 保存可重复起点和预期结果。
3. 先证明旧配置会稳定失败。
4. 修 harness/提示/工具后证明通过。
5. 加入核心回归集并标记来源类别。

一次真实失败通常比十个想象的 benchmark 更能指出 harness 的薄弱处。
