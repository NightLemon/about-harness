# 实验方法

Agent 系统有随机性、版本漂移和环境噪声。实验的目标不是消灭所有噪声，而是让结论足以指导选择，并知道结论适用到哪里。

## 1. 写假设

```text
在 12 个 TypeScript 日常修改任务上，保持模型、提示和工具不变，
把推理强度从 low 提到 medium，会把一次通过率提高至少 10 个百分点，
且 P90 总时长不超过原来的 1.5 倍。
```

这个假设包含任务集、对照、变量、指标和接受门槛。

## 2. 固定实验清单

每次运行保存：

- 模型精确 ID/快照、provider 与认证方式；
- harness 名称、版本、surface 与配置 commit；
- system/project/task prompt 版本；
- 工具列表、schema 版本、MCP/extension 版本；
- 推理强度、上下文/输出上限、重试预算；
- 仓库 commit、依赖锁、OS/container、网络策略；
- 任务 ID、起始状态和验收脚本版本。

无法固定的服务端变化至少记录日期与区域。

同时保存默认基线与工程基线。前者使用 harness 推荐默认，后者只加入会用于日常生产的项目指令、验证和安全边界。不要让候选配置拥有只针对评测答案的隐藏提示或工具。


## 3. 设计任务集

每个任务包含干净起点、给 agent 的输入、机器可执行检查、人工 rubric 和禁止动作。避免把答案泄露在测试名称或提示里。保留一部分未用于调优的 holdout 任务，防止对公开集过拟合。

```yaml
id: auth-refresh-race-01
category: debugging
timeout_minutes: 20
must_pass:
  - npm run test -- auth/refresh
  - npm run typecheck
must_not:
  - change token TTL
  - add production dependency
human_rubric:
  root_cause: 0-2
  minimal_change: 0-2
```

## 4. 重复与随机化

每个配置—任务组合至少运行 3 次；高方差或高价值任务增加到 5–10 次。随机交错 A/B 顺序，避免某一配置总在缓存热或服务低负载时运行。独立 run 使用干净 worktree/container，不共享模型可见的历史。

优先使用配对设计：同一任务在 A/B 都运行，再比较任务内差异，避免某配置碰巧分到更简单任务。提前定义超时、provider 5xx、runner 崩溃等基础设施失败是否重跑以及最多几次；保留原失败记录，不能看到结果后再排除“不好看”的 run。

## 5. 评分

优先级从高到低：

1. 安全与禁止动作是否满足（硬门禁）；
2. 确定性检查是否通过；
3. 任务质量 rubric；
4. 人工纠正次数与完成率；
5. 总时长、token、调用成本；
6. 工具错误、重复读取与恢复能力。

报告均值之外，也报告中位数、P90、最差案例和失败类型。小样本的 100% 不代表真实成功率 100%。

对二元成功率给出样本量和区间（小样本可用 Wilson 区间），不要只报百分比。区分：

- **single-run success**：一次真实调用成功，最贴近日常默认体验；
- **success within budget**：允许预先规定的重试/人工轮次后成功；
- **best-of-k / pass@k**：多次采样至少一次成功，不能冒充一次成功率；
- **task-level success** 与 **run-level success**：一个任务重复多次，run 不是完全不同的任务样本。

模型 judge 要盲化配置名和候选顺序，随机/轮换展示顺序，并用人工标注集检查一致性。事实测试能确定的项目不要交给主观 judge。

## 6. 一次改变一个主要变量

先单变量筛选，再对最有希望的组合做小型因子实验。例如先固定模型调工具集，再固定工具集比较 low/medium，最后比较两个模型。若一次变四项，只能评价整体配置，不能解释原因。

## 7. 阅读失败轨迹

将失败分为：目标理解、上下文检索、规划、工具选择、执行、验证、安全、预算/基础设施。每类抽样轨迹，区分模型决策问题、harness 反馈问题和任务本身有歧义。

## 8. 设晋级规则

```text
新配置只有在：
1) 零安全违规；
2) 关键任务成功率不下降；
3) 加权总体成功率提高 ≥ 5 个百分点；
4) P90 成本增长 ≤ 20%；
才成为默认。
```

阈值应由业务风险决定，不必照抄示例。

## 9. 持续评测

模型/harness/工具升级、项目结构大改或失败分布变化时重跑。每次生产失败如果能脱敏并稳定复现，就加入回归集。排行榜回答“别人任务上的平均”，持续评测回答“我的工作现在是否变好”。
