# 模型—Harness 匹配

“哪个模型最好”缺少三个必要条件：做什么任务、运行在哪个 harness、受什么成本与风险约束。更准确的问题是：**哪个模型—harness 配置在目标任务分布上达到最高的可接受效用？**

## 从一个指定模型开始的完整顺序

```text
确认身份 → 验证协议 → 做能力探针 → 建立默认基线 → 收集真实任务
→ 按失败类型调一个变量 → 重复 A/B → 设置路由/回退 → 写入适配卡
```

### 0. 确认身份与协议

先记录精确模型 ID/快照、provider、API/订阅认证、harness 版本和 surface。同一营销名称可能指向不同快照；`latest`、`default` 之类别名会漂移。不要问模型“你是什么版本”作为唯一证据，应从模型选择器、API 响应元数据、provider 日志或 harness 状态读取。

在真实任务前做协议 smoke test：纯文本、一次结构化工具调用、工具报错后的修正、多轮工具调用、长输出截断、取消/超时与流式事件。若 adapter 丢失 tool call ID、参数或错误，提高推理强度也不能修复。

## 先写模型能力假设

不要从模型宣传语直接推出配置。先建立可被实验推翻的假设：

| 维度 | 要观察什么 | 可能的 Harness 对策 |
| --- | --- | --- |
| 指令遵循 | 长规则、否定约束、局部 override 是否稳定 | 缩短常驻指令；把强规则移到 hook/策略 |
| 工具调用 | 选工具、填参数、读取错误、重试是否可靠 | 减少工具；简化 schema；提供调用示例 |
| 代码与领域能力 | 能否理解目标语言、框架、仓库规模 | 提供权威入口；增加检索或专用 skill |
| 长上下文 | 信息在不同位置时是否仍能利用 | 检索优先；状态文件；调整压缩策略 |
| 规划 | 多步任务是否保持目标、顺序和依赖 | 显式计划；小步 checkpoint；外部任务状态 |
| 自我验证 | 是否主动运行测试、修正失败 | 在任务契约中写验证；用 hook/policy 强制门禁 |
| 不确定性 | 缺证据时是否猜测 | 要求标明假设；提供只读搜索；设升级条件 |
| 延迟与成本 | 首 token、总时长、token、缓存利用 | 调低推理；分流简单任务；稳定提示前缀 |

这里写的是“假设”，不是模型本性。模型版本、provider 适配器和 harness 工具格式变化后都要重测。

## 用小探针校准假设

在完整任务集前跑 6 个 2–5 分钟探针。它们用于发现配置断裂，不用于给模型排总榜。

| 探针 | 最小任务 | 观察信号 |
| --- | --- | --- |
| 指令作用域 | 根规则与子目录 override 有一处明确差异 | 是否找到并采用更具体规则 |
| 检索 | 在小仓库定位一个未给路径的实现 | 读取文件数、引用路径、是否猜测 |
| 工具恢复 | 第一次调用返回可修正参数错误 | 是否读懂错误并只重试必要调用 |
| 状态保持 | 10–15 步任务中途插入无关长日志 | 目标/禁区/已改文件是否保留 |
| 验证闭环 | 给一个会失败的测试和可修 bug | 是否运行、读取、修正并复跑 |
| 安全边界 | README 内含诱导上传模拟 secret 的文字 | 是否把它当数据并拒绝越权动作 |

探针失败时先查加载、工具、adapter 与权限。只有证据显示模型已看到正确状态且仍判断失败，才把问题记入模型能力假设。

## 再写工作负载画像

以过去真实工作抽取 10–30 个代表任务，至少覆盖：

- 小而确定的修改；
- 多文件功能或重构；
- 带失败日志的调试；
- 陌生代码库调查；
- 需要外部资料/工具的任务；
- 有安全边界或不可修改项的任务；
- 长会话、压缩或中断恢复；
- 模型应该拒绝或请求授权的负面任务。

给每类任务一个真实频率权重。若 70% 工作是小修，不能让一个只出现一次的复杂任务决定默认模型。

## 可调旋钮

按以下顺序优化，能减少变量混淆：

1. **环境正确性**：工作目录、依赖、认证、权限、网络是否可用。
2. **任务契约**：目标、上下文入口、约束、完成条件是否清楚。
3. **验证反馈**：模型是否能运行并读懂测试、构建或视觉检查。
4. **上下文供给**：持久指令、检索、工具输出和压缩是否合适。
5. **工具表面**：工具数量、描述、schema 与错误返回。
6. **推理与模型**：再选择模型、推理强度、路由与重试预算。
7. **高级编排**：skills、hooks、subagents、MCP、扩展。

很多“换大模型才解决”的问题，其实在第 1–4 步就能修复，而且对所有模型有效。

## 保留两个基线

- **默认基线**：目标 harness 的推荐默认设置，只提供任务必要信息。它回答“开箱能否使用”。
- **工程基线**：加入短项目指令、正确验证和最小安全边界，但没有针对单个 benchmark 的特例。它回答“合理配置后的常态”。

后续调优应与工程基线比较，同时保留默认基线以衡量配置维护的真实收益。如果必须靠大量任务专用提示才领先，结论应标为对任务集过拟合风险。

## 建立路由而不是单一默认

常见的三档路由：

| 路由 | 任务 | 配置倾向 |
| --- | --- | --- |
| 快速 | 格式转换、已知小修、检索 | 快/低成本模型，低推理，窄工具集 |
| 标准 | 日常功能、测试、一般调试 | 均衡模型，中等推理，完整本地工具 |
| 深度 | 架构、疑难调试、高风险评审 | 强模型，高推理，先计划，额外验证者 |

升级条件应该可观察：例如目标测试两次失败且失败原因不同、多目录依赖尚不明确、或需要比较三种以上架构权衡。不要只用“看起来很难”。

## 效用函数

可以把决策写成：

```text
效用 = 任务成功率 × 业务价值
     - 延迟成本 - token/调用成本 - 人工介入成本 - 风险惩罚
```

无需强行把所有项换算成货币。可设置硬门槛：安全违规为零、关键任务通过率 ≥ 95%、P90 时长 ≤ 15 分钟；过门槛后再比较成本。

## 不要这样优化

- 同时更换模型、提示、工具与权限，然后把结果归因给模型。
- 只跑一次任务；agent 输出有随机性，环境也有噪声。
- 用模型自己给自己的答案打唯一分数。
- 只记录成功，不保留失败轨迹和人工纠正次数。
- 为 benchmark 写特殊提示，却把结论推广到全部真实工作。
- 只比最终代码，不比危险动作、延迟和维护成本。
