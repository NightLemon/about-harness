# 提示与任务契约

对 agent 来说，高质量提示更像一份小型任务契约，而不是“神奇咒语”。它说明结果、上下文入口、真实边界和可执行的完成条件，同时给模型保留选择实现路径的空间。

## 四段式模板

```md
## 目标
修复用户会话超时后刷新失败的问题。

## 上下文
- 从 `src/auth/` 和现有 token refresh 测试开始。
- 错误日志：`fixtures/refresh-error.txt`。

## 边界
- 不改变 access/refresh token 的有效期。
- 不添加生产依赖，不修改公开 API。
- 缺信息时先调查；涉及数据库迁移时停下说明。

## 完成条件
- 先写出能稳定复现的失败测试，再做最小修复。
- 运行目标测试、认证测试集和类型检查。
- 最终报告根因、改动文件、验证命令与结果。
```

只写会改变结果的内容。文件路径、失败症状、兼容性和验收比“认真、全面、逐步思考”更有用。

## 任务大小决定交互协议

### 小任务

直接要求执行与验证。过度计划会让简单任务变慢。

```text
把 docs 里的旧命令 npm test 改为 npm run check；只改文档，运行文档检查。
```

### 中型任务

允许 agent 先探索，但要求在关键假设上用证据。

```text
调查支付重试为何重复扣款。先复现并说明根因；确认方案后实现，运行目标端到端测试。
```

### 大型或高风险任务

分成探索、方案、实施、验证和人工验收；关键决定应写到可恢复的项目记录，避免压缩丢失；指定何时需要人批准。

## 用引用替代复制

引用文件、日志和权威文档，让 agent 通过工具读取。复制整个仓库说明既耗上下文又容易陈旧。对长日志先给错误附近片段和完整文件路径；对网页说明来源可信度与需要核对的具体事实。

## 写边界，而不是写操作录像

除非流程本身受监管，不必规定每个 shell 命令。写明：不得改什么、可以改到哪里、何种外部动作需确认、缺证据时如何处理。让模型在边界内选择路径，通常比微操每一步更稳健。

## 让完成可观测

“确保没问题”不可执行。“运行 `npm run check` 并修复失败；报告退出码与仍未运行的检查”可执行。UI 任务提供参考图和目标视口；数据任务提供 schema 与样例；研究任务要求来源、日期和不确定项。

## 失败后的提示修正

第一次失败时不要立即把提示加倍变长。先分类：

- 没看到信息：给入口或改善检索。
- 看到了但忽略：缩短冲突规则，强调可测试约束。
- 不会使用工具：改工具描述/schema 或给一个正确调用。
- 能做但没验证：加入完成门禁。
- 基础能力不足：提高推理/换模型，或拆小任务。

把同一纠正出现两次的稳定规则移入项目指令；把特定工作流移入 skill；必须执行的规则移入 hook/CI。

## 提示版本化

用于评测和自动化的提示应有版本号或 Git commit。记录模板版本、注入变量和渲染后的摘要。否则模型不变但提示悄悄改变，实验结论就不可复现。
